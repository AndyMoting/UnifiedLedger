# RG-01 普通支出设计

## 1. 目的

本设计冻结首个公开匿名黄金场景 `RG-01` 的业务答案，用于验证一笔手工普通支出从确认入账到余额、统计、对账和修改历史的完整闭环。

本设计只规定可观察的账务行为和机器可比较的预期结果，不提前固定数据库表名、客户端界面或序列化字段名。后续实现不得为了迁就代码结果反向修改本设计；如需改变业务答案，应先更新对应账务规则和决定记录。

## 2. 范围

`RG-01` 覆盖：

- 手工创建一笔使用资产账户付款的普通支出。
- 必填字段校验与人工确认入账。
- 同币种复式分录平衡。
- 账户余额、消费、现金流和净资产变化。
- 无外部凭证时的分录级待对账状态。
- 只修改备注时的版本替代和资金结果不变。
- 重复提交时只产生一次资金影响。

`RG-01` 不覆盖导入、自动分类、候选匹配、预算规则、复杂订单、退款、转账、借贷、余额不足限制、网络、同步或智能建议。这些能力由其他场景独立验证。

## 3. 固定数据

场景使用以下完全合成的数据：

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-01` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种 | `CNY` |
| 金额精度 | `2` |
| 账本 ID | `ledger-a` |
| 付款资产账户 ID | `asset-bank-a` |
| 付款账户显示名 | 银行卡 A |
| 期初权益账户 ID | `equity-opening-a` |
| 一级分类 ID | `expense-category-food` |
| 一级分类显示名 | 餐饮 |
| 二级分类 ID | `expense-category-breakfast` |
| 二级分类显示名 | 早餐 |
| 隐藏费用账户 ID | `expense-account-breakfast` |

名称只用于显示，稳定 ID 才是关联和比较依据。

## 4. 前置状态

测试不得直接覆盖银行卡余额。场景开始前存在一笔有效的期初余额交易：

| 交易 ID | 时间 | 账户 | 分录金额 |
| --- | --- | --- | ---: |
| `tx-opening-a` | `2026-01-01T00:00:00+08:00` | `asset-bank-a` | `+1000.00 CNY` |
| `tx-opening-a` | `2026-01-01T00:00:00+08:00` | `equity-opening-a` | `-1000.00 CNY` |

两条分录合计为零。支出发生前，银行卡 A 的重放余额为 `1000.00 CNY`，账本没有其他有效交易。

## 5. 创建普通支出

### 5.1 用户操作

用户选择手工记账并填写：

- 业务类型：支出。
- 金额：`35.80 CNY`。
- 二级分类：`expense-category-breakfast`，显示为“餐饮 > 早餐”。
- 付款账户：`asset-bank-a`。
- 统计时间：`2026-01-15T08:30:00+08:00`。
- 备注：空。

用户执行保存即构成本次明确的人工确认。该操作不经过导入解析或候选确认流程。

### 5.2 正式交易

保存成功后创建一笔当前有效版本的正式交易 `tx-expense-rg01`，并生成且仅生成以下两条有效分录：

| 分录 ID | 账户 | 金额 | 含义 |
| --- | --- | ---: | --- |
| `posting-expense-rg01` | `expense-account-breakfast` | `+35.80 CNY` | 早餐费用增加 |
| `posting-bank-rg01` | `asset-bank-a` | `-35.80 CNY` | 银行卡资产减少 |

两条分录按 `CNY` 合计为零。分类 ID 关联到隐藏费用账户，用户分类与真实金融账户保持为不同维度。

## 6. 余额与统计结果

交易生效后必须得到以下结果：

| 验收维度 | 预期结果 |
| --- | ---: |
| 银行卡 A 余额变化 | `-35.80 CNY` |
| 银行卡 A 期末余额 | `964.20 CNY` |
| `2026-01-15` 消费 | `35.80 CNY` |
| `2026-01` 消费 | `35.80 CNY` |
| `2026-01-15` 现金流支出 | `35.80 CNY` |
| `2026-01` 现金流支出 | `35.80 CNY` |
| 收入 | `0.00 CNY` |
| 净资产变化 | `-35.80 CNY` |
| 预算结果 | 不适用 |

“预算结果不适用”表示场景没有预算配置，不得被解释为消费为零。余额和所有统计必须来自同一笔当前有效的正式交易。

## 7. 对账与证据

手工确认是该交易的入账依据，但不是外部金融凭证：

- `posting-bank-rg01` 属于真实资产账户，初始对账状态为“待对账”。
- `posting-expense-rg01` 属于费用账户，不设置金融账户对账状态。
- 交易列表汇总显示“待对账”。
- 场景中不存在外部证据引用、匹配记录、推断候选或差异记录。
- 待对账状态不改变交易有效性、余额或报表结果。

以后出现银行流水时，可以在独立对账流程中补充证据并更新对账状态，但不得再创建一笔支出。该后续行为不属于 `RG-01` 的执行步骤。

## 8. 备注修改与版本历史

创建完成后，用户把备注从空修改为“早餐”。系统必须：

1. 保留创建时的旧版本，并将其标记为已被新版本替代。
2. 创建备注为“早餐”的当前有效版本。
3. 保持正式交易的稳定身份不变。
4. 保持两条资金分录的账户、金额、币种和有效资金结果不变。
5. 保持银行卡余额、消费、现金流、收入、净资产和对账状态不变。

修改完成后，系统仍只有一笔有效支出和一次 `35.80 CNY` 的资金影响。不得重复扣款、重复统计或重置未变化资金分录的对账结果。

## 9. 校验与幂等

金额必须大于零，且必须选择付款账户和可用的二级支出分类。缺少任一必填项时：

- 保存失败并返回可定位到字段的校验结果。
- 不创建正式交易或分录。
- 不改变余额、统计、版本或对账状态。

同一次保存操作因连续点击、客户端重试或处理结果重放而重复提交时，只能得到同一笔正式交易。重复提交后的余额和统计必须与首次成功后的结果完全一致，不得产生第二组有效分录。

不同的、由用户再次明确发起的真实支出即使字段相同，也不应仅因金额、时间、分类和账户相同而被误判为重复。具体提交标识的物理字段由实施计划确定。

## 10. 机器可比较契约

后续实现使用版本化 JSON 表达本场景的固定输入和预期输出，并由共享核心测试读取。JSON 至少需要表达：

- 场景元数据、固定时区、币种和精度。
- 初始账户、分类、期初交易和余额。
- 手工创建与备注修改两个有序操作。
- 每个阶段的当前有效交易、全部分录和版本关系。
- 余额、统计、对账、证据和禁止副作用断言。
- 重复提交与必填字段失败的反例。

金额必须使用精确十进制字符串或整数最小货币单位，不得使用二进制浮点数。业务无关的列表顺序在比较前按稳定 ID 归一化。JSON 的字段命名和模式版本在实施计划中确定，本设计中的业务值不得改变。

## 11. 验收标准

`RG-01` 只有同时满足以下条件才算通过：

- 创建结果严格包含一笔有效普通支出和两条平衡分录。
- 银行卡余额为 `964.20 CNY`，消费与现金流支出各为 `35.80 CNY`。
- 收入为零，净资产减少 `35.80 CNY`，预算为不适用。
- 无外部凭证时，真实账户分录和交易汇总均为待对账。
- 只改备注后保留两个版本，但仍只有一次有效资金影响。
- 必填字段失败时产生零个有效资金分录。
- 同一次保存操作重复提交时不产生第二笔资金影响。
- 场景在关闭网络、同步和所有可选智能能力后仍得到相同结果。
