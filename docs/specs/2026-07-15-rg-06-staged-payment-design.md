# RG-06 分阶段付款设计

## 1. 目的

本设计冻结公开匿名黄金场景 `RG-06` v1 的定金与尾款业务答案。它验证固定应付总额、两笔独立实际付款、未付金额零账务影响、独立付款进度与履约状态、导入确认、精确证据绑定、分录级对账、镜像合并和幂等结果。

本设计只规定可观察的账务、报告和状态行为，不固定数据库、界面或平台实现。取消、退款与定金损失、修正、混合资金、合并项目和全额付款后分摊分别由 `RG-07`、`RG-12`、`RG-04`、`RG-05` 和 `RG-11` 冻结，v1 不组合这些能力。

## 2. 固定数据与独立基线

场景使用完全合成的数据：

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-06` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种与精度 | `CNY`，两位小数 |
| 付款账户 | `asset-bank-a`，资产账户 A |
| 二级支出分类 | `expense-category-service`，服务 > 生活服务 |
| 隐藏费用账户 | `expense-account-service` |
| 应付总额 | `300.00 CNY` |
| 定金 | `80.00 CNY`，`2026-04-28T10:00:00+08:00` |
| 尾款 | `220.00 CNY`，`2026-05-03T16:30:00+08:00` |
| 关联组 | `staged_payment`，显示名“分阶段付款” |

手工路径和导入路径分别从相同独立基线运行，不互相累计。基线通过平衡的期初交易建立资产 A `1000.00 CNY` 和期初权益 `-1000.00 CNY`；测试不得直接覆盖余额。

## 3. 非财务关联组

用户先手工创建应付总额 `300.00 CNY` 的分阶段付款组。创建只保存系统管理的关联组、单一二级支出分类和应付展示状态：已付 `0.00`、待付 `300.00`。此时不存在付款、正式交易、分录、消费、现金流或对账变化，资产 A 仍为 `1000.00`。

关联组使用稳定 ID，并在每个阶段保存完整状态历史。历史记录状态事实和付款引用，但状态记录自身不生成分录。普通账目不创建通用订单生命周期。

## 4. 两笔独立实际付款

用户在 `2026-04-28T10:00:00+08:00` 明确保存定金 `80.00 CNY`，创建第一笔正式支出交易：

| 分录账户 | 金额 |
| --- | ---: |
| 生活服务费用 | `+80.00 CNY` |
| 资产账户 A | `-80.00 CNY` |

定金后资产 A 为 `920.00`。当日消费和现金流出均为 `80.00`，收入为 `0.00`，净资产变化为 `-80.00`。关联组已付 `80.00`、待付 `220.00`；待付金额没有负债、应付、余额、消费、现金流、收入、净资产或对账影响。

用户在 `2026-05-03T16:30:00+08:00` 明确保存尾款 `220.00 CNY`，创建第二笔独立正式支出交易：

| 分录账户 | 金额 |
| --- | ---: |
| 生活服务费用 | `+220.00 CNY` |
| 资产账户 A | `-220.00 CNY` |

尾款后资产 A 为 `700.00`。尾款日消费和现金流出均为 `220.00`，收入为 `0.00`，净资产变化为 `-220.00`；累计消费和现金流出均为 `300.00`。两笔付款分别保存稳定付款、交易、费用分录和资产分录身份。付清或完成状态不得再创建第三笔交易或重复任何消费与现金流。

## 5. 付款进度与履约状态

关联组分别保存：

- `payment_progress`：`unpaid`、`partially_paid` 或 `paid_in_full`，只根据已经明确确认的实际付款计算。已付为 `0.00` 时必须是 `unpaid`；已付大于 `0.00` 且待付大于 `0.00` 时必须是 `partially_paid`；待付为 `0.00` 时才可以是 `paid_in_full`。
- `fulfillment_status`：`in_progress` 或 `fulfilled`，由用户明确控制。

用户可以在支付定金后、仍待付 `220.00` 时把履约状态改为 `fulfilled`。此时界面分别显示“履约：已交付”和“付款：待付 220.00”。状态变化追加历史，但交易、分录、余额、统计和对账逐字段保持不变。尾款确认后付款进度成为 `paid_in_full`，履约状态仍独立保留。完成确认也只追加状态历史，不重复账务影响。

## 6. 时间与来源事实

每笔付款使用自己的实际付款时间作为正式交易发生时间和默认统计时间。导入来源中的付款时间不可变，后续确认和状态操作不得覆盖。定金与尾款分别进入自己的日期和月份统计；关联组创建、履约变化、付清确认和完成确认时间均不改变报告归属。

## 7. 导入、角色绑定与确认

定金和尾款来源分别生成独立 `pending_confirmation` 候选。即使金额、时间和银行证据完整，导入也不构成正式确认。候选明确保存来源、证据、不可变付款时间、规则版本和置信度；确认前正式交易、分录、付款、消费、现金流和对账变化均为零。

确认必须在同一原子边界校验不可变导入来源与证据，并明确指定既有 `staged_payment` 组、`deposit` 或 `final` 角色、二级支出分类和付款资产账户的精确绑定。角色不明确的候选保持待确认，`guessed_payment_role` 为 `null`，不得依据金额、时间或导入顺序推断。候选状态变成 `confirmed` 本身不授权正式交易或对账；只有上述原子确认整体成功，定金才创建第一笔交易、尾款才创建第二笔交易，并把已绑定证据核验的精确 `payment_asset` 分录直接建立为 `matched`。每笔统计时间默认等于其不可变来源付款时间。

## 8. 证据与对账

每笔银行证据只链接其付款交易的资产分录。定金和尾款交易独立处于待对账或已核对状态；费用分录不适用金融对账。关联组可以把付款对账汇总为 `pending`、`partial` 或 `complete`，但交易与关联组状态均只从精确分录对账事实派生，不是独立写入授权，也不改变任何余额或报表。

手工路径创建每笔付款时分别建立 `pending` 的资产分录对账：两笔都待对账时关联组为待对账，定金精确证据链接只把定金分录从 `pending` 改为 `matched` 并使组成为部分对账，尾款精确证据链接后才完全对账。导入路径在不可变证据与精确绑定的原子确认成功时，为对应资产分录直接建立 `matched` 对账。未确认 intake 没有正式分录或对账；后到镜像或重复证据只并入原付款并保持既有 evidence link 与对账状态不变。所有这些对账动作的余额、报告与现金流 delta 均为零。

## 9. 校验与冻结失败

以下输入全部拒绝：总额或付款金额非正数；两阶段定金大于或等于总额；尾款不等于当前待付金额；付款超过待付金额；币种混合；分类缺失、一级、停用或非支出；付款账户未知、非金融、不属于用户或为负债；待付金额大于零时确认 `paid_in_full`。

每次失败都明确字段和原因，保持对应操作前的完整基线，包括余额、统计、关联组金额、状态、历史与对账。不得为通过校验而猜测角色、账户、分类或建立隐藏分录。

## 10. 幂等与完整状态

相同关联组创建、手工付款、履约变化、完成确认、导入来源、候选确认和证据请求重试时返回原稳定 ID。重试不新增候选、交易、分录、版本、付款、关联组、历史或证据链接，也不重复消费和现金流。

机器答案保存手工完成态与导入完成态的完整快照，包括交易、当前版本、分录、付款、关联组、状态历史、候选、来源、证据链接、余额、统计和对账。幂等重试后的两份快照必须逐字段相等。

## 11. 领域恢复契约

`StagedPayment` 通过公开、结构化且 catalog-free 的 snapshot factory 恢复。snapshot 保留 raw relation member rows，并分别使用 transaction、version、posting-set 和 posting DTO 表达尚未验证的正式交易输入，不接受已构造的 `FormalTransaction` 充当持久化输入；恢复不 replay command，不使用 opaque aggregate serialization，也不把不变量下放给 adapter。领域按确定性首错顺序返回 RG-06 专属失败：重复 relation row 在构造领域 set 前按第二次出现的 row index 拒绝，再校验 relation 精确成员、正总额与 nonnegative checked arithmetic、连续且严格递增的 append-only history、合法零效果事件、`[]`/`[deposit]`/`[deposit, final]` 阶段顺序与金额/时间、各 identity kind 内唯一性、来源 instant/text 成对结构，以及 installment 与正式交易的一一对应和当前分录身份。

每个 raw posting set 必须先通过既有公开 `PostingSet.create` 重建，再由这些 posting sets 调用 `FormalTransaction.create`；任一 posting set 或正式交易链无效都按对应 formal row 返回 `InvalidSnapshot(FORMAL_TRANSACTION, index)`。formal rows 必须按 `[deposit, final]` 与 installment rows 同序且逐项一一对应，交换顺序即使 transaction ID 集合相同也无效。已有合法多版本交易可以恢复，但 current posting set 必须仍包含 installment 保存的精确 expense/payment posting IDs、金额、付款账户与时间。历史 category/account catalog 漂移不参与恢复；后续新命令仍必须通过当前 catalog 准入。来源时间按已保存的 RFC 3339 instant/text 结构恢复，不重新套用当前 offset policy。snapshot 输入、嵌套正式账务图和恢复后 aggregate 的对外集合均做防御性复制。金额/账户修正导致的付款分录身份变化仍属于后续修正范围。

## 12. 机器可比较契约

机器答案使用 `schema_version: 1`。所有金额是两位小数十进制字符串，所有正式分录明确使用 `CNY`，所有场景、请求、来源、候选、交易、版本、分录、付款、关联组、历史、证据和匹配均使用稳定 ID。

共享校验器负责场景信封、精确金额、稳定 ID、逐币种平衡、分录唯一性和余额重放。针对性测试冻结非财务建组、两笔独立付款、报告时点、独立状态、完整历史、候选零影响、角色歧义、明确绑定、证据目标、对账汇总、镜像合并、完整幂等快照、输入校验和范围边界。

## 13. 验收标准

`RG-06` v1 只有同时满足以下条件才通过：

- 期初、定金和尾款交易分别平衡，资产 A 依次为 `1000.00`、`920.00` 和 `700.00`。
- 定金日消费与现金流出为 `80.00`，尾款日均为 `220.00`，累计均为 `300.00`，收入为零，净资产累计减少 `300.00`。
- 待付 `220.00` 只存在于关联组展示状态，严格没有财务、报告或对账影响。
- `staged_payment` 关联组保存稳定总额、已付、待付和两笔精确付款身份，不创建通用订单生命周期。
- 履约状态可在待付时成为已履约，付款进度仍显示待付；所有状态变化保留历史且零账务影响。
- 每笔导入在明确确认和精确组/角色绑定前保持待确认与零影响，角色歧义不被猜测。
- 银行证据只链接对应资产分录，两笔交易独立对账，组汇总和镜像合并不改变金额。
- 所有无效输入保持精确基线，所有重试保持完整状态相等，范围外组合未被提前实现。
