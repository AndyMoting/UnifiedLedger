# RG-03 账户互转与手续费设计

## 1. 目的

本设计冻结公开匿名黄金场景 `RG-03` v1 的业务答案，用于验证用户自有真实金融账户之间的一对一同币种互转、显式手续费、导入待确认和镜像证据合并。真实金融账户可以是资产或负债；本场景选择资产账户到资产账户作为具体黄金示例。

本设计只规定可观察的账务行为和机器可比较结果，不固定数据库、界面或平台实现。组合转账保留为 `future_draft`，不属于本版本答案。

## 2. 范围

`RG-03` v1 覆盖：

- 用户自己的一个转出真实金融账户与一个转入真实金融账户之间的一对一 `CNY` 互转；两端允许是资产或负债账户。
- 转出 `60.00`、到账 `59.00`、手续费 `1.00` 的三分录答案。
- 手工保存作为明确确认并立即创建正式交易。
- 完整导入来源只创建待确认候选，确认前不产生正式账务影响。
- 用户确认导入候选后创建正式交易，后到镜像证据只合并证据和更新对账。
- 未确认去向的单边扣款保持待确认，不使用补平或暂记账户。
- 请求重试、重复导入和镜像证据重放的幂等结果。

以下内容不属于 `RG-03` v1：一对多、多对一或多对多组合转账，跨币种转账，信用还款、理财买入或赎回，手续费退回，以及目标余额调整。组合转账保留为 `future_draft`；手续费退回由 `RG-07` 冻结，目标余额调整由 `RG-09` 冻结。

## 3. 固定数据

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-03` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种 | `CNY` |
| 金额精度 | `2` |
| 账本 ID | `ledger-a` |
| 转出账户 | `asset-bank-a`，银行卡 A |
| 转入账户 | `asset-wallet-b`，支付钱包 B |
| 期初权益账户 | `equity-opening-a` |
| 手续费分类 | `expense-category-transfer-fee`，金融费用 > 转账手续费 |
| 手续费费用账户 | `expense-account-transfer-fee` |

稳定 ID 是关联和比较依据，显示名不参与身份判断。本例两个资产账户均属于用户本人；该选择不排除规则允许的自有负债账户。

## 4. 前置状态

每条主流程从同一独立基线运行，不继承其他流程的结果。基线由一笔有效期初交易建立：

| 分录账户 | 金额 |
| --- | ---: |
| `asset-bank-a` | `+1000.00 CNY` |
| `asset-wallet-b` | `+100.00 CNY` |
| `equity-opening-a` | `-1100.00 CNY` |

期初交易逐币种平衡，两个真实资产账户的重放余额分别为 `1000.00` 和 `100.00`。测试不得直接覆盖余额。

## 5. 正式账务答案

转账本金为内部流转。转出账户总扣款 `60.00` 由转入本金 `59.00` 和对外手续费 `1.00` 共同解释：

| 分录账户 | 金额 | 含义 |
| --- | ---: | --- |
| `asset-bank-a` | `-60.00 CNY` | 转出资产减少，包含本金和手续费 |
| `asset-wallet-b` | `+59.00 CNY` | 转入资产增加 |
| `expense-account-transfer-fee` | `+1.00 CNY` | 转账手续费费用增加 |

三条分录合计为零。手续费使用默认二级分类“金融费用 > 转账手续费”。本金不进入收入、消费或对外现金流；手续费进入 `1.00` 消费和 `1.00` 现金流出，净资产减少 `1.00`。交易后余额为银行卡 A `940.00`、支付钱包 B `159.00`。

## 6. 手工保存

用户明确选择两个自有真实金融账户、转出金额、到账金额、手续费和发生时间。执行保存即构成明确人工确认，不创建导入候选。本例两端恰好都是资产账户。

保存成功后创建且仅创建一笔正式交易和上述三条有效分录。没有外部证据时，两个真实资产分录均为待对账，手续费分录不适用金融账户对账，交易汇总为待对账。对账状态不改变余额或统计。

转出账户与转入账户必须不同，且都必须是用户自己的真实金融账户；资产与负债账户均可满足该账户类型要求。币种必须一致；转账本金和转出金额必须大于零；`转出金额 = 到账金额 + 手续费`。缺少账户、未知账户、非本人账户、非金融账户、零或负本金以及金额不平衡均校验失败，并产生零正式交易、零分录、零版本和零对账变化。

## 7. 导入候选与确认

完整导入来源可以明确转出账户、转入账户、转出金额、到账金额、手续费和币种，但导入本身不构成确认。首次导入按以下顺序处理：

1. 保存不可覆盖的来源事实和证据引用。
2. 创建一个状态为 `pending_confirmation` 的候选，记录确定性规则、来源引用、置信度和待确认字段。
3. 不创建正式交易或分录，不改变余额、统计或对账状态。

用户随后明确确认该候选时，创建一笔与第五节相同经济结果的正式转账。来源端扣款证据匹配转出资产分录；转入资产分录仍待镜像证据；手续费分录不适用对账。交易汇总为部分匹配。

候选确认属于明确人工确认，但不把来源推断提升为自动入账规则。来源事实、候选、确认和正式交易的稳定引用必须共同保留。

## 8. 镜像证据合并

转入账户的镜像来源后到时，系统必须识别它属于已确认的同一资金流，并合并到原证据链：

- 保持正式交易 ID、版本 ID、分录集合和全部金额不变。
- 将镜像证据关联到转入资产分录，并把两个资产分录及交易汇总更新为已匹配。
- 不创建第二笔转账、第二组分录、收入或新的统计影响。
- 不覆盖先到来源；两份证据及各自来源引用都保留。

重复导入任一来源或重复处理镜像证据时，候选、正式交易、分录、证据关联、余额和统计均保持幂等。

## 9. 未知单边扣款

只有转出账户扣款事实且没有已确认转入账户时，系统只能创建待确认候选。候选必须明确标记 `destination_account_id` 待用户确认，并产生以下零影响：

- 零正式交易和分录。
- 零余额、消费、现金流、收入和净资产变化。
- 零正式对账关联。
- 不创建平衡、暂记、悬挂或其他隐藏补平账户与分录。

资料不足不是制造形式平衡的授权。只有明确确认完整去向后才可创建正式交易。

## 10. 机器可比较契约

机器答案沿用 `RG-01` 和 `RG-02` 的 `schema_version: 1`，并增加场景专用的有序导入生命周期、证据链和来源字段。共享校验器仍负责场景信封、稳定引用、精确金额、逐币种平衡、分录唯一性和余额重放；针对性测试冻结转账、统计、候选和镜像合并语义。

所有金额均使用两位十进制字符串，不使用 JSON 数字。机器答案必须包含稳定元数据、账户和分类、平衡期初交易、手工结果、有序导入操作、精确分录与余额、统计、对账、证据、来源、幂等和禁止副作用。

## 11. 验收标准

`RG-03` v1 只有同时满足以下条件才通过：

- 手工保存创建一笔三分录平衡转账，余额为 `940.00` 和 `159.00`。
- 本金的收入、消费和对外现金流均为零；手续费产生 `1.00` 消费、`1.00` 现金流出和 `-1.00` 净资产变化。
- 完整来源在确认前只有一个待确认候选，正式资金和统计影响为零。
- 确认后只创建一笔正式转账，先到证据只匹配对应真实账户分录。
- 镜像证据合并后保持同一交易和分录集合，只更新证据与对账，不产生重复收入或统计。
- 未知单边扣款保持待确认，且不使用任何补平账户。
- 所有重试和来源重放保持幂等；网络、同步和可选智能能力关闭时答案不变。
