# RG-05 合并付款设计

## 1. 目的

本设计冻结公开匿名黄金场景 `RG-05` v1 的合并付款业务答案。它验证两个独立消费项目共享一次资产扣款时的平衡分录、消费记录、分类统计、系统管理关联组、导入确认、证据归属、对账、异常分配和幂等结果。

本设计只规定可观察的账务与报告行为，不固定数据库、界面或平台实现。一个项目使用多个资金账户、分阶段或未付款金额、退款和后续修正分别由 `RG-04`、`RG-06`、`RG-07` 和 `RG-12` 冻结；多项目多资金来源不属于 v1。

## 2. 固定数据与独立基线

场景使用完全合成的数据：

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-05` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种与精度 | `CNY`，两位小数 |
| 付款账户 | `asset-bank-a`，资产账户 A |
| 项目 A | `40.00 CNY`，生活 > 日常用品 |
| 项目 B | `60.00 CNY`，服务 > 生活服务 |
| 关联组 | `merged_payment`，显示名“合并付款” |

手工路径和导入路径分别从同一独立基线运行，不互相累计。基线通过平衡的期初交易建立资产 A `1000.00 CNY` 和期初权益 `-1000.00 CNY`，测试不得直接覆盖余额。

## 3. 手工合并付款

用户在 `2026-04-10T18:30:00+08:00` 明确保存一次 `100.00 CNY` 资产付款，同时确认项目 A `40.00` 和项目 B `60.00`。正式账本只创建一笔交易：

| 分录账户 | 金额 |
| --- | ---: |
| 项目 A 费用账户 | `+40.00 CNY` |
| 项目 B 费用账户 | `+60.00 CNY` |
| 资产账户 A | `-100.00 CNY` |

三条分录按 `CNY` 合计为零，资产 A 余额重放为 `900.00`。只存在一条资产付款分录和一次现金流，不创建清算账户、虚假借记、隐藏补平或第二笔扣款。

## 4. 独立消费记录与关联组

项目 A 和 B 分别形成稳定的用户可见消费记录。每条记录保存自己的 ID、二级分类、明细、金额、币种、原始项目时间和对应费用分录，不因共享付款而合并。

系统建立一个 `merged_payment` 关联组。关联组由系统管理，显示名为“合并付款”，只引用一笔正式交易和其中唯一资产分录。两个稳定项目分配分别绑定消费记录、对应费用分录、分类、金额和币种；分配总额必须严格等于 `100.00 CNY`。关联组不产生第二笔交易、额外分录或通用订单生命周期。

## 5. 统计时间与金额口径

v1 只支持同一 `CNY` 币种和一个共同实际付款时间。两条消费记录统一使用 `2026-04-10T18:30:00+08:00` 作为统计时间；项目 A 和 B 的原始时间分别作为不可变来源事实保存，不允许项目级统计时间覆盖。

付款日结果固定为：

| 维度 | 结果 |
| --- | ---: |
| 消费 | `100.00 CNY` |
| 项目 A 分类消费 | `40.00 CNY` |
| 项目 B 分类消费 | `60.00 CNY` |
| 现金流出 | `100.00 CNY` |
| 收入 | `0.00 CNY` |
| 净资产变化 | `-100.00 CNY` |
| 预算 | 不适用 |

原价 `112.00`、优惠 `12.00` 和实付 `100.00` 只解释结算过程。优惠不产生资产、收入、费用或其他分录。

## 6. 导入、分配与确认

完整导入来源可以同时提出银行扣款和两个项目，但导入本身不构成确认。首次处理只创建 `pending_confirmation` 候选并保留来源、凭证时间、规则版本和置信度；正式交易、分录、版本、消费记录、项目分配、关联组、余额、统计和对账变化均为零。

只有用户明确确认候选及两个二级分类后，才创建与手工路径相同经济结果的一笔正式交易、两个消费记录、两个项目分配和一个关联组。

项目分配只有 `90.00` 时保留 `10.00` 缺口并继续待确认；项目分配达到 `110.00` 时标记冲突。两种情况均不得猜测缺失项目、分类或账户，不得使用隐藏账户或补平分录，正式和对账影响保持为零。

## 7. 证据与对账

银行扣款证据只链接 `posting-asset-rg05-imported`，并驱动唯一真实账户分录和交易汇总的财务对账。两个费用分录不适用金融账户对账。

项目收据只链接其精确项目分配。业务证据完整度独立保存为无、部分或完整；项目证据不得改变资产分录或交易的财务对账状态。后到的项目 B 镜像证据合并到原项目 B 分配，不能创建第二笔交易、分录、版本、消费记录、项目分配、关联组或现金流。

## 8. 校验与冻结失败

以下输入全部拒绝且保持零交易、分录、版本、消费记录、项目分配、关联组和对账变化：分类缺失、一级分类、停用分类、非支出分类；付款总额或项目金额为零或负数；分配合计不等于付款；项目 ID 重复；付款账户未知、非真实金融账户或不属于用户；项目币种混合。

每次失败都保留原基线余额和零统计变化。系统不得依据金额差额猜测分类、项目、资金账户或隐藏平衡方式。

## 9. 幂等与完整状态

相同手工请求、导入来源、确认请求和后到证据重试时，返回原有稳定 ID。重试不新增候选、交易、分录、版本、消费记录、项目分配、关联组或证据链接，也不重复现金流。

机器答案保存手工完成态和导入完成态的完整快照，包括候选、交易、当前版本、分录、消费记录、项目分配、关联组、证据链接、余额、统计、财务对账和业务证据完整度。幂等重试后的快照必须逐字段相等。

## 10. 机器可比较契约

机器答案使用 `schema_version: 1`。所有金额是带两位小数的十进制字符串，所有正式分录明确使用 `CNY`，所有场景、请求、来源、候选、交易、版本、分录、消费记录、项目分配、关联组、证据和匹配均使用稳定 ID。

共享校验器负责场景信封、精确金额、稳定 ID、逐币种平衡、分录唯一性和余额重放。针对性测试另行冻结消费独立性、唯一资产分录、统计与分类合计、候选零影响、明确确认、证据精确目标、独立完整度、异常分配、完整幂等快照、输入校验和范围边界。

## 11. 验收标准

`RG-05` v1 只有同时满足以下条件才通过：

- 项目 A `40.00`、项目 B `60.00` 和资产 A `-100.00` 构成一笔平衡正式交易。
- 两条消费记录保留独立稳定 ID、分类和明细，同时只存在一条资产分录和一次现金流。
- 付款日消费 `100.00`、分类消费 `40.00` 与 `60.00`、现金流出 `100.00`、收入 `0.00`、净资产变化 `-100.00`，预算不适用。
- `merged_payment` 关联组绑定两个精确项目分配和唯一实际付款，并显示“合并付款”。
- 导入在明确确认前保持待确认和零正式影响；分配缺口不被猜测，过度分配成为冲突。
- 银行证据只驱动资产分录财务对账，项目收据只驱动独立业务证据完整度。
- 镜像、重复来源和所有重试不重复任何金额、项目、关联组或证据链接，完整状态快照保持相等。
- 所有无效输入保持基线余额以及零正式、统计和对账影响，范围外业务未被提前实现。
