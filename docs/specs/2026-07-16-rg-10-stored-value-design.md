# RG-10 商户储值充值与消费设计

## 状态与范围

本设计冻结 `RG-10` v1 的公开匿名黄金答案，级别为 `core_required`，币种为 `CNY`，账本时区为 `Asia/Shanghai`。主路径假设用户已经明确建立并启用某商户的受限储值资产账户。未启用该账户时沿用 `D-050` 的充值即支出模型；同一笔事件不得在两种模型之间混用。

本设计覆盖充值、赠送额、批次、消费、到期、既有余额接入、导入确认和分录级对账。退款、取消、外汇、转让或现金赎回、商户破产、税务、负余额、非面值可用积分和完整历史重建留待后续规则。

## 账户与金额

储值账户是由用户持有的、已启用的、只能在指定商户或范围内使用的受限资产，正式余额按商户可核对的面值保存。实付额和赠送额是充值批次的来源组成，不拆成两个正式资产账户。赠送差额使用专用特殊非现金赠送权益收入账户，不能进入普通现金收入。

所有正式金额必须是精确两位十进制字符串，不接受 JSON 数字或浮点。实付和到账必须大于零，赠送可以为精确零或正数但不得为负数。充值满足：

```text
credited_amount = paid_amount + bonus_amount
```

主例的充值为实付 `1000.00`、到账 `1200.00`、赠送 `200.00`。正式交易为储值资产 `+1200.00`、银行 A `-1000.00`、赠送权益收入 `-200.00`，按 CNY 平衡。

## 主路径

### 充值

充值确认必须同时确认启用的储值账户、实际付款银行账户、实付、到账、赠送组成、币种、实际发生时间和来源证据。充值交易保存 `occurred_at`、`statistics_at`、`effective_at` 和 `created_at`；实际经济时间与确认创建时间独立。

充值后报告为：现金流出 `1000.00`，消费 `0.00`，普通现金收入 `0.00`，特殊非现金赠送权益收益 `200.00`，净资产变化 `+200.00`。储值余额为 `1200.00`。RG-10 v1 不适用预算执行，因此充值的 `budget_effect` 为 `0.00`。

### 消费

主例随后确认储值消费 `300.00`，使用明确的二级支出分类。交易为费用 `+300.00`、储值资产 `-300.00`。报告为消费 `300.00`、现金流 `0.00`、普通收入 `0.00`、特殊收入 `0.00`、净资产变化 `-300.00`，储值剩余 `900.00`。充值不产生消费，消费不产生第二条银行现金流。消费的 `budget_effect` 仍为 `0.00`，只有这笔实际消费产生 `300.00` 的 `category_effect`。

批次消费顺序由商户分配证据优先控制。没有该证据时按最早到期日、载入时间、稳定批次 ID 排序。机器样例分别包含更早到期、同到期但更早载入、以及同到期同载入但稳定 ID 不同的批次，必须依次证明三层比较键。排序只分配面值，不推断 paid-first 或 bonus-first；若分配未说明组成，批次的 paid/bonus 剩余组成标记为 `unknown`。同一消费跨多个批次时必须逐批记录金额、顺序和证据，商户分配引用的证据 ID 必须解析到已定义证据。

### 到期

有效期日期、提醒或状态变化不产生交易和报告影响。只有明确确认余额确实失效，才创建到期损失交易：储值资产减少、专用到期损失费用增加，现金流和预算影响为零，净资产按损失减少。到期确认保留批次、历史消费、原充值和失效证据；不得删除、覆盖或重新计算旧交易。用户确认或业务失效证据只证明失效事实，不自动将储值资产分录标记为已核验；没有精确账户余额证据时，金融分录保持 `pending`。

## 既有余额接入

启用时的现有余额以接入日期和明确的接入前余额调整进入储值资产。机器样例把 `600.00` 接入余额重放为储值资产 `+600.00`、专用调整权益 `-600.00` 的平衡正式交易，明确保存四个时间、版本、用户确认、来源证据和审计关系；普通收入、普通费用、消费、预算、分类与现金流均为零，净资产变化为 `+600.00`。该调整不是充值、普通收入，也不猜测实付/赠送组成；启用边界前事件保持原来模型。补齐历史后，以 `replace_not_append` 语义用真实历史替代调整，任一时刻只允许调整或重建历史之一生效，原调整、版本和来源继续追加保留。完整历史重建算法仍不在本设计范围内。

## 证据、导入与对账

银行付款证据使用职责 `bank_payment_posting`，只链接银行资产分录。商户余额或充值回执使用职责 `stored_value_credit_lot`，只链接储值资产分录和批次；赠送关系可用独立职责 `stored_value_bonus_component`。职责不能互换。银行腿和商户腿可以分别部分或完全核验，对账只改变证据状态，不改变余额或报告。

充值或消费导入必须保持 `pending_confirmation`，直到行为/模型、由用户持有且正确类型的付款与储值账户、实付额、到账额、赠送额、实际时间、批次事实、消费分类和分配全部明确确认。即使充值或消费导入的全部字段已经齐全，只要缺少明确确认，也只能保存待确认候选且正式影响为零。商户余额不能证明银行付款；银行流水不能证明商户到账或赠送额。充值、消费、到期确认、提醒、两条证据核验、两类导入、接入调整和商户批次分配的相同输入重试都必须返回原稳定 IDs，并保持完整正式、接入和对账状态不变。

## 原子拒绝与禁止效果

拒绝浮点或 JSON 数字、非正实付、非正到账、负赠送、credited 小于 paid、组成不闭合、未知或未启用账户、账户类型错误、模型重叠、消费或到期超过余额/批次、无效批次分配、未确认到期、猜测组成和未确认导入。每个拒绝样例必须命名唯一的操作前基线和相同结果状态，并明确断言交易、分录、批次、版本、调整、确认、报告、候选、来源、证据、审计与对账增量全部为零；无效批次分配使用消费后剩余 `900.00` 的命名基线。禁止负储值资产、隐藏清算分录、充值重复消费、普通现金赠送收入、提前到期损失和证据越权。

## 版本与验收

机器答案为 `golden/rules/rg-10.json`。它包含充值、消费、提醒零影响、确认到期、三层批次分配、接入边界、完整与不完整导入待确认、证据部分对账、全操作幂等重试和拒绝输入的命名状态。测试从交易重放余额，从交易类型与批次变更独立推导报告，比较完整命名状态并验证先前实体和历史前缀追加不变；修改任一交易、批次、证据、确认、审计或历史引用都必须被测试发现。
