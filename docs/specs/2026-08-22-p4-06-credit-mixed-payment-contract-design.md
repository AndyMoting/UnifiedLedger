# P4-06 信用与混合支付契约

**Status:** approved（2026-08-22 用户批准 O-1..O-8；独立规格评审 findings P406-SPEC-001..007 已修复闭合）

## 1. 目的与范围

本契约承载 RL-05（信用消费、还款和退款生命周期）与 RL-06（资产与信用账户混合支付）两个 `core_required` 场景（`GOLDEN_TESTS.md:174-175`）。契约一次冻结（O-1）；实施分两片，RL-05 信用先、RL-06 混合后，各需独立实施授权（§9）。

本文件只冻结核心语义：来源路由归宿、三个新 kind、三腿生命周期、候选与确认门、evidence 基数、持久化边界原则与匿名验收断言。具体 kind token 标识符、列形状、诊断码、迁移 SQL 与完整 state oracle 粒度留实施批规格登记（D-104 契约先例）。

对 P4-05 的两处冻结条款，本契约按 D-102 跨规格登记修订先例进行登记修订：收/付款方式列（列 7）处置与「信用借还」拒行归宿（§2.2）。本契约不改变 D-097 已批准的 ordinary v1 与 D-100 已批准的 transfer v2 normalized source 合同；不引入 D-103（P4-08）之外的 matcher/evidence-link/reconciliation 写入语义；不改变 D-104/D-105 已批准的重复候选与关闭记录行为，仅在其上层叠加信用与混合行族。

方向记法约定（全文适用）：分录符号一律为正式账本记法——费用正、收入账户负、负债余额负值表示欠款（`ACCOUNTING_RULES.md:14` 借正贷负与负债负余额总则、`:102` 算例）。外部锚点与裁决速记若以「欠款增减」表达（如"负债腿 +8.80"指欠款增加 8.80），登记时按下述冻结算例换算：信用消费的负债资金分录为负（欠款增加、余额转负），信用还款与信用退款的负债分录为正（欠款减少、余额回零方向），依据 `ACCOUNTING_RULES.md:102-104`、`D-058` 与 `D-072`（资产 `-50.00`、信用负债 `+50.00` 的还款算例）。

## 2. 来源事实层（O-2）

### 2.1 收/付款方式列白名单解冻

现状锚点：P4-05 冻结列 7「收/付款方式」不持久化、不解析（P4-05 规格 §2.4，该列表行）；取证确认其为组合 token——`&` 连接多个支付腿，腿呈现「机构名(####)」机构名+掩码尾号定长模式（P4-05 规格 §3.1）。「信用借还」分类行现为类型化拒行并登记移交本批（`AlipaySourceTokens.kt:48-51`；P4-05 规格 §3.2「信用借还 → P4-06」行）。

本契约解冻为路由列，冻结条款：

- 提取范围收窄为白名单：仅提取「支付腿种类 token」（如花呗族、余额宝族、银行卡机构类等冻结集合的成员）；掩码账号与尾号（`机构名(####)` 的括号部分）不提取、不解析、不持久化。
- 开放域原则（与 P4-05 token 域同构）：支付方式 token 随年份扩张，任何封闭全域枚举必失效；本契约只冻结两个集合——腿种类白名单（已核实语义的 token，按信用腿/资产腿两类语义登记）与其外的一切 token（UNKNOWN）。白名单外腿种类 token 产生类型化拒行，fail-closed、零写入；白名单扩张只经显式合同修订（行为证据 + 独立评审），实现不得静默接受新 token。
- 具体白名单 token 清单由实施批规格以行为证据核定后冻结；本契约冻结清单的语义分类原则与 fail-closed 政策。
- 隐私边界：腿种类 token 仅用于路由与候选 provenance；不落盘掩码尾号或账号；收/付款方式列除腿种类 token 外的任何内容不进入事实或持久化。仅含资产腿种类的普通行不因本列产生任何持久化事实（「列 7 零落盘」对普通行维持）。
- 本批全部 fixture 必须来源中立、全合成；不得使用真实掩码尾号、商户、商品、订单号、账号锚点或个人关系信息。

## 3. 领域与应用合同（O-3/O-4/O-5）

### 3.1 三 kind 与 contract_version=3（O-3）

- spine 新增恰三个 record kind（语义冻结）：信用消费源（含退款变体）、信用还款源、混合支付源；对应恰三个 candidate kind。不设第四 kind：信用退款行归入信用消费 kind 的退款变体，在候选层以语义标记区分，正式化按 RG-07 退款合同语义（`D-078`）。kind token 最终标识符留实施批规格（P4-02 命名纪律；`ordinary_flow_source`/`transfer_flow_source` 先例）。
- 三个新 kind 全部固定 `contract_version=3`；kind→version 封闭派生并由持久层配对 CHECK 拒绝错配（D-100 第 9 条先例）。ordinary v1（D-097）与 transfer v2（D-100）既有行不重写、不升级。

### 3.2 信用负债账户持有前置（O-4）

- 信用消费、混合支付负债腿与信用退款的候选确认，必须由用户显式指定一个该用户已持有的信用负债账户；候选不得携带猜测账户。
- 不得由解析器、spine 或候选流程自动创建信用负债账户；未指定或指定账户未被用户持有时，候选保持待确认（不可确认路径，零正式写入）。
- 还款资金资产账户同样由用户显式指定：腿种类 token 可作人工确认的输入建议，不构成账户映射（D-032 手工两端显式选择先例）。
- 共享负债账户（跨来源族或跨账本共用同一负债账户映射）属迁移配置，不进产品核心（D-053：私人账户、别名、锚点与特殊修正不得进入公开核心，由迁移工具承载）；产品核心不内置任何默认负债账户或默认账户映射。

### 3.3 三腿生命周期语义（O-5）

1. **信用消费**（无资产腿）：费用 `+` / 负债 `-`（欠款增加，余额转负，界面按欠款显示）；购买日现金流出为零、消费按全额确认一次（`ACCOUNTING_RULES.md:42`、`:102`；`D-058`）。
2. **信用还款**：独立 `CREDIT_REPAYMENT` 交易类型，不得以 `ACCOUNT_TRANSFER` 代替（`D-072`）；本金两腿 资产 `-` / 负债 `+`（欠款减少）；还款日现金流出为本金，消费、收入与净资产变化均为零，不重复原消费（`ACCOUNTING_RULES.md:104`；`D-058`）。
3. **信用退款**：独立经济事件（非冲正、非版本修正、不吞并原消费版本）；费用 `-` / 负债冲减（欠款减少，正式记法负债 `+`）；与原交易建立退款关联（RG-07 退款合同语义复用，`D-078`）；原期间消费不变，退款期冲减消费并按负债方向登记资金效应。
4. **利息、手续费、逾期费**：无锚点样本，登记 future_rule（金融费用分类）；本契约不冻结其分录形状，不得由实现默认值发明入账路径。

## 4. 混合支付候选与确认（O-6）

- 导入候选默认 `pending_confirmation`；确认前零正式交易、分录、关联组、余额、报表与对账效果（`ACCOUNTING_RULES.md:106`）。
- 确认门：全部腿金额完整（各腿精确金额、各腿账户——含 §3.2 显式指定的负债账户——与用户确认的二级分类）方可确认多腿分录；费用合计 = 资产腿 + 负债腿合计（`ACCOUNTING_RULES.md:100/:102`）。
- 缺腿或腿金额不完整：候选保持资料不足（incomplete），不猜测账户、不隐藏账户、不以暂记分录补平（`ACCOUNTING_RULES.md:106`；D-073 缺腿候选先例）；补全后可再确认，路径幂等。
- `constraint_solved` 反推只作为人工确认的输入建议：以候选级建议呈现，携带 provenance 与 confidence；永不自动入账、不产生任何正式效果、不得回写来源事实（D-097 事实分层）。
- 禁止基线与调整重复计入：同一经济效果只允许一套最终分录；候选确认创建正式交易后，不得再以调整、推断或镜像名义追加第二套分录、第二笔交易或重复消费/现金流（消除外部基线「占位 + 反推」双记形态，§7.2）。
- 幂等与镜像：相同请求与等价来源重放返回原稳定结果，零新写入；后到镜像证据只追加 lineage，不建第二笔交易（matcher/evidence-link 语义按 D-103；重复来源处置按 D-104）。

## 5. evidence 基数登记（O-7）

本批是 D-103 O-4「场景显式登记基数」的首个场景登记。总则：一行来源 evidence ↔ 一笔交易（evidence:transaction 恒 1:1）——「恒 1:1」约束的是一行来源 evidence 对应恰一笔交易（不拆单），后到镜像证据按 D-103 追加链接（evidence:transaction 可为多对一）不违反本条；场景差异体现在交易内 evidence:posting 基数：

| 行类型 | evidence:transaction | evidence:posting（真实资金分录） |
| --- | --- | --- |
| 信用消费（单信用腿） | 1:1 | 1:1（负债腿） |
| 混合支付（资产腿+负债腿） | 1:1 | 1:N（同一 evidence 关联全部资金腿：资产腿+负债腿） |
| 信用还款 | 1:1 | 1:1（资产腿） |
| 信用退款 | 1:1 | 1:1（负债腿） |

- 费用分录不参与 evidence link 与对账记录（`D-072` 先例）。
- 不设全局默认基数；本登记只覆盖 P4-06 行族（D-103 O-4 纪律），其余场景基数仍由各自场景合同登记。

## 6. 持久化边界（O-8 原则）

- 全部 P4-06 持久化需求冻结为恰一次 schema 版本推进 v24→v25 的单个加性迁移，覆盖三类结构：多腿 decision snapshot 扩展、信用/混合 candidate、`mixed_payment` 关联组产品表。
- 两片实施合计只允许这一次版本推进；迁移交付时点（片 1 或片 2）由实施授权登记，两片不得各自推进 schema 版本。
- 复用 RG-04/RG-07 已冻结的合同语义（`D-072`/`D-073`/`D-078`：`CREDIT_REPAYMENT`、混合分录方向、缺腿候选、退款关联、幂等），不复制 `rg04_*`/`rg07_*` 竖井 owner 表——竖井表只作行为证据先例（D-103 现状侦察纪律）。
- 列形状、表名、触发器与迁移 SQL 留实施批规格登记；本契约批准前不得预先创建 schema 或 runtime。

## 8. 排除项

1. 分期付款（多期未来扣款）：future_rule（D-049；`ACCOUNTING_RULES.md:196` 分摊与分期不得混用）。分期型信用支付方式的单行在本契约只按当日已发生经济效果入账，不建立未来扣款计划。

## 9. 实施批切分（O-1）
