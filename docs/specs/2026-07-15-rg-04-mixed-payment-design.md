# RG-04 混合支付设计

## 1. 目的

本设计冻结公开匿名黄金场景 `RG-04` v1 的混合支付业务答案。它验证一笔消费由资产和信用负债共同出资时的平衡分录、消费与现金流时点、信用还款、系统管理关联组、导入确认、分录级对账、镜像证据和幂等结果。

本设计只规定可观察的账务与报告行为，不固定数据库、界面或平台实现。退款、合并付款、分阶段或未付款金额以及后续分录修正分别由 `RG-07`、`RG-05`、`RG-06` 和 `RG-12` 冻结。

## 2. 固定数据与独立基线

场景使用完全合成的数据：

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-04` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种与精度 | `CNY`，两位小数 |
| 资产账户 | `asset-bank-a`，资产账户 A |
| 信用负债账户 | `liability-credit-b`，信用负债 B |
| 二级支出分类 | `expense-category-daily`，生活 > 日常用品 |
| 隐藏费用账户 | `expense-account-daily` |
| 关联组类型 | `mixed_payment`，显示名“混合支付” |

手工生命周期和导入生命周期分别从同一独立基线运行，不互相累计。基线通过一笔平衡的期初交易建立资产 A `1000.00 CNY` 和期初权益 `-1000.00 CNY`；负债 B 的重放余额为 `0.00 CNY`。测试不得直接覆盖余额。

## 3. 手工混合支付

用户在 `2026-02-10T12:00:00+08:00` 手工保存一笔 `120.00 CNY` 消费，选择二级分类并确认以下付款组成：

| 资金来源 | 付款组成 | 正式分录 |
| --- | ---: | ---: |
| 资产账户 A | `70.00 CNY` | `-70.00 CNY` |
| 信用负债 B | `50.00 CNY` | `-50.00 CNY` |

保存构成明确人工确认，不创建导入候选。正式交易还包含费用分录 `expense-account-daily +120.00 CNY`，三条分录按 `CNY` 合计为零。交易后资产 A 余额为 `930.00`，负债 B 余额为 `-50.00`；界面按负债正常方向显示欠款 `50.00`。

资金组成合计必须严格等于费用。金额必须大于零，分类必须是可用二级支出分类，每个资金账户必须是已知真实资产或负债账户。任何校验失败都产生零正式交易、零分录、零关联组和零状态变化。

## 4. 消费与现金流时点

购买日的报告结果固定为：

| 维度 | `2026-02-10` 结果 |
| --- | ---: |
| 消费 | `120.00 CNY` |
| 现金流出 | `70.00 CNY` |
| 收入 | `0.00 CNY` |
| 净资产变化 | `-120.00 CNY` |
| 预算 | 不适用 |

消费按业务费用总额确认一次。现金流只按当日实际减少的资产资金确认；负债增加代表融资，不是购买日资产现金流出。原价 `135.00`、优惠 `15.00` 和结算价 `120.00` 只解释结算过程，优惠不生成资产、收入、费用或其他正式分录。

## 5. 信用本金还款

用户在 `2026-03-05T09:00:00+08:00` 使用资产 A 偿还负债 B 的 `50.00 CNY` 本金。手工保存创建一笔业务类型为 `credit_repayment` 的正式交易：

| 分录账户 | 金额 |
| --- | ---: |
| `asset-bank-a` | `-50.00 CNY` |
| `liability-credit-b` | `+50.00 CNY` |

两条分录平衡。还款后资产 A 余额为 `880.00`，负债 B 为 `0.00`。还款日现金流出 `50.00`，消费、收入和净资产变化均为 `0.00`，预算不适用。购买与还款生命周期累计消费仍为 `120.00`，累计现金流出为 `120.00`；本金还款必须记录为还款，不得复制原费用或原消费。

## 6. 混合支付关联组

正式购买必须具有一个系统管理、具体命名的关联组：

- 稳定类型为 `mixed_payment`，用户显示名为“混合支付”。
- 关联一笔业务或费用交易的稳定 ID。
- 每个付款组成直接引用该交易中已经存在的真实资产或负债 `Posting`，并保存账户、币种和正向展示金额。
- 付款组成合计为 `120.00 CNY`，与费用分录严格相等。
- 关联组只表达业务金额与资金组成的关系，不是第二笔正式交易，不产生额外分录或报告影响。

普通用户看到“混合支付”及资产 A `70.00`、信用负债 B `50.00` 的付款组成。系统不得引入抽象订单入口或通用订单生命周期。

## 7. 导入、补全与确认

完整导入来源可以提出总额、二级分类和两个资金组成，但导入本身不构成确认。首次处理必须：

1. 保存来源事实、证据引用、规则版本和置信度。
2. 创建状态为 `pending_confirmation` 的候选，明确要求用户确认分类、资金组成和正式交易创建。
3. 产生零正式交易、零分录、零关联组、零余额与报告变化，并且不改变对账。

用户明确补全并确认分类、资产 A `70.00` 和负债 B `50.00` 后，才创建与手工答案相同经济结果的一笔正式购买和一个 `mixed_payment` 关联组。候选变为已确认，来源、候选和确认引用全部保留。

若来源只证明总额 `120.00` 和资产 A `70.00`，剩余 `50.00` 必须作为待确认资金缺口保存。系统不得猜测负债 B，不得建立隐藏平衡账户、暂记账户或补平分录；确认前的所有正式影响仍为零。

## 8. 分录级对账与证据

费用分录不适用金融账户对账。每条真实资产或负债分录独立保存对账状态和证据链接：

- 资产扣款证据只能链接 `posting-asset-rg04-imported`。
- 资产分录已匹配而负债分录待对账时，交易汇总状态为部分对账。
- 后到的负债镜像证据只能链接 `posting-liability-rg04-imported`。
- 两条真实账户分录都已匹配时，交易汇总状态为完全对账。

证据和对账状态不改变交易 ID、版本、分录、余额或报告。镜像证据不得创建第二笔交易、第二组分录、第二次费用、消费或现金流。

## 9. 幂等与禁止副作用

相同手工请求、来源记录、候选确认请求或镜像证据重复处理时，必须返回原有候选、交易、关联组或证据链接。重试不得新增候选、交易、分录、版本、关联组或证据链接，也不得重复费用、消费或现金流。

场景明确禁止自动确认导入候选、猜测资金账户、隐藏补平、通用订单生命周期、优惠分录、网络、同步或可选智能能力。关闭这些可选能力后结果必须完全相同。

## 10. 机器可比较契约

机器答案沿用 `schema_version: 1`。所有金额均为带两位小数的十进制字符串，所有正式分录均明确 `CNY`，并使用稳定的场景、交易、分录、候选、来源、证据和关联组 ID。

共享校验器负责场景信封、稳定 ID、精确金额、逐币种平衡、分录唯一性和余额重放。针对性测试另行冻结手工购买、信用还款、报告时点、负债显示、候选零影响、用户确认、关联组身份、分录级对账、精确证据链接、缺失资金腿、幂等、校验失败和范围边界。

## 11. 验收标准

`RG-04` v1 只有同时满足以下条件才通过：

- 购买创建费用 `+120.00`、资产 `-70.00`、负债 `-50.00` 的三条平衡分录。
- 购买日消费 `120.00`、现金流出 `70.00`、收入 `0.00`、净资产变化 `-120.00`，负债显示欠款 `50.00`。
- 还款创建资产 `-50.00`、负债 `+50.00` 的正式信用还款，现金流出 `50.00` 且不重复消费。
- `mixed_payment` 关联组只连接一笔购买与其两条现有资金分录，并显示“混合支付”和付款组成。
- 完整导入在确认前仍只有待确认候选和零正式影响；缺失资金腿不被猜测或隐藏补平。
- 一条真实账户分录已匹配、另一条待对账时汇总为部分对账；镜像证据精确链接后汇总为完全对账。
- 所有请求、来源和证据重试保持幂等，且范围外业务未被提前实现。
