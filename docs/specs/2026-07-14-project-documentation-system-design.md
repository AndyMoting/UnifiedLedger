# 项目文档体系设计

## 1. 目的

本设计建立一套可持续维护的项目文档体系，使需求、账务规则、技术架构、关键决定和当前进度不依赖临时讨论记录。仓库内文档是项目的正式依据，本地协作说明和历史参考资料不构成正式规则。

文档体系需要达到以下目标：

- 新的工作阶段能够快速恢复准确上下文。
- 每项确认结论只有一个明确的主要归属。
- 代码行为、测试和文档保持同步。
- 关键决定能够追溯，但旧结论不会与新结论并存生效。
- 仓库不包含个人数据、本机信息、临时讨论记录或开发工具痕迹。

## 2. 权威来源

项目知识按以下优先级解释：

1. 仓库内最新且状态明确的正式文档。
2. 已合入 `main` 的代码和通过的自动化测试。
3. 经过确认但尚未迁移的历史材料。
4. 讨论记录和外部参考材料。

当文档与代码行为冲突时，不直接假定任何一方正确。应暂停相关变更，核验对应决定、测试和实现，再在同一工作项中修正冲突。

## 3. 文档组成与职责

### 3.1 `README.md`

作为中文项目入口，提供项目概览、当前成熟度、技术栈摘要、两到四条最常用的快速验证命令和正式文档索引。它不重复详细需求、架构、账务规则或完整开发命令。

### 3.2 `docs/PROJECT_CHARTER.md`

记录项目存在的原因、范围边界、非目标和成功标准。该文档应保持稳定，只有项目方向发生根本变化时才修改。

### 3.3 `docs/PRODUCT_REQUIREMENTS.md`

记录已经确认的用户可见行为、主要工作流和功能边界。它描述系统做什么，不规定具体技术实现。

### 3.4 `docs/ACCOUNTING_RULES.md`

记录账户、交易、`Posting`、转账、借贷、预付、退款、修正和对账等领域规则，并使用匿名示例解释边界情况。

### 3.5 `docs/ARCHITECTURE.md`

记录系统分层、核心模型、模块职责、数据流、接口边界和不可破坏的技术约束。它也是生产技术栈和版本策略的权威来源，覆盖目标平台、语言、UI、存储、序列化、依赖管理、构建系统和测试框架。每项技术选择必须标记为“已确定”“候选”或“暂缓决定”。实现细节只有在影响模块契约时才进入该文档。

### 3.6 `docs/DECISIONS.md`

按唯一的 `D-xxx` 编号记录重要决定、理由、影响范围和取代关系。决定正文保持简洁，详细规则写入其所属文档。

### 3.7 `docs/ROADMAP.md`

记录未来阶段、开发顺序、阶段目标和进入下一阶段的验收门槛，不承担当前任务清单或历史日志的职责。

### 3.8 `docs/CURRENT_STATE.md`

记录当前已完成事项、正在进行的检查点、已知阻塞、当前环境差异和唯一下一步。它是恢复工作上下文时首先读取的文件，不保存长期历史，也不复制完整技术栈或命令清单。

### 3.9 `docs/GOLDEN_TESTS.md`

记录核心验收层级、匿名规则场景、真实来源验证边界和隐私要求。它描述必须验证的行为，不复制测试实现。

### 3.10 `docs/CONTRIBUTING.md`

记录开发流程、分支策略、提交规范、合并规则、文档同步要求、验证门槛和隐私约束。它也是本地开发环境和可执行命令的权威来源，覆盖初始化、构建、测试、格式化、静态检查、文档检查、隐私检查、调试和发布构建。

## 4. 语言与命名

- 正式文档和提交说明以中文为主。
- 文件名、代码标识符、类型名、API 名称和命令保持英文。
- `Transaction`、`Posting`、`SourceRecord` 等代码类型不强制翻译。
- 中文领域术语首次出现时可以附英文名称，后续使用统一称呼。
- 文档不得使用难以检索的同义词反复指代同一概念。

## 5. 更新流程

### 5.1 开始工作

1. 首先读取 `docs/CURRENT_STATE.md`。
2. 根据任务读取相关需求、账务规则、架构和决定。
3. 核验当前分支、工作树状态和适用的验证命令。

### 5.2 确认决定

1. 讨论过程不逐句写入仓库。
2. 结论确认后，为重要决定分配 `D-xxx` 编号。
3. 将决定摘要写入 `docs/DECISIONS.md`。
4. 同步更新决定所属的需求、账务规则或架构文档。
5. 被取代的决定保留原文并明确指向新编号，不直接删除。

### 5.3 修改代码

当代码行为变化时，相关实现、测试和正式文档必须在同一个逻辑工作项中完成。测试通过不能替代文档更新，文档完整也不能替代行为验证。

### 5.4 结束工作

每个稳定检查点结束前更新 `docs/CURRENT_STATE.md`，确保它准确说明当前状态和唯一下一步。临时探索、失败尝试和已经完成的短期过程不长期保留在该文件中。

### 5.5 技术栈与命令维护

- 只有已经确认的生产技术选择才能在 `docs/ARCHITECTURE.md` 中标记为“已确定”。
- 研究工具、迁移原型和辅助脚本不会自动成为生产技术栈。
- 候选方案必须说明待验证问题，不得写成已经采用的事实。
- 完整本地命令只在 `docs/CONTRIBUTING.md` 中维护。
- 命令以仓库根目录为执行起点，使用相对路径，不包含本机绝对路径。
- 每条正式命令必须可以直接复制执行，并注明必要前置条件。
- 命令变化时，代码、`docs/CONTRIBUTING.md` 和相关测试在同一工作项中更新。
- `README.md` 中的快速命令必须来自 `docs/CONTRIBUTING.md`，不得形成第二套定义。
- `docs/CURRENT_STATE.md` 只记录暂时不可用的命令、环境阻塞或当前阶段尚不存在的工程入口。

## 6. 提交规范

- 一个提交只表达一个可以独立理解的逻辑变化。
- 提交前必须完成适用测试、隐私检查和文档同步。
- 功能代码、对应测试和必要文档通常放在同一个提交中。
- 纯重构与行为修改尽量分开提交。
- 不提交临时调试内容、半成品、真实账务数据或工作中标记。
- 提交信息采用英文类型加中文说明，例如 `feat: 增加精确金额模型`。
- 常用类型包括 `feat`、`fix`、`refactor`、`test`、`docs` 和 `chore`。
- 每个稳定提交后可以推送，结束当前工作前至少推送一次。

## 7. 分支与合并

### 7.1 分支策略

- `main` 始终保持可运行且测试通过。
- 纯文档修正和极小的安全修改可以直接提交到 `main`。
- 新功能、底层模型、解析器、数据迁移和对账逻辑使用短期任务分支。
- 一个分支只对应一个明确目标，不按工作窗口创建分支。
- 未完成实验不得合入 `main`。

### 7.2 合并门槛

重要代码变更通过 Pull Request 合入。合并前必须满足：

- 分支已经同步最新 `main`，冲突已解决。
- 所有适用测试和隐私检查通过。
- Pull Request 说明包含目的、行为变化、验证结果和相关决定编号。
- 代码、测试和正式文档已经同步。
- 所有审查问题已经解决，并完成一次完整自审。

### 7.3 合并方式

- 默认使用 merge commit，保留独立提交和功能分支边界。
- 只有提交确实琐碎且无法独立理解时才允许 squash merge。
- 不使用 rebase merge 合入 `main`。
- 只允许在尚未被他人依赖的个人任务分支上整理提交历史。
- 合并后删除本地和远端任务分支。
- 禁止强制推送或删除 `main`。

仓库支持时，应为 `main` 配置规则：要求状态检查通过，禁止强制推送和删除，并要求合并前解决审查讨论。单人阶段不强制外部批准或签名提交。

## 8. 旧资料迁移

旧资料只作为迁移来源，不整篇复制。迁移步骤如下：

1. 逐条识别已经确认的结论。
2. 核验结论是否仍然有效、是否与现有实现或其他决定冲突。
3. 将有效内容改写为中立、明确的正式规则。
4. 按职责写入唯一的主要文档，并在需要时登记决定编号。
5. 将无法确认或存在冲突的内容标记为待讨论，不写成现行规则。
6. 删除个人信息、本机位置、外部项目名称和讨论措辞。

首次迁移完成后，新仓库文档成为唯一正式依据，旧资料降级为历史证据。

## 9. 一致性与隐私检查

自动检查至少覆盖：

- 失效的仓库内文档链接。
- 重复或格式错误的决定编号。
- `TODO`、`TBD` 和其他未完成占位符。
- 本机绝对路径、个人信息和真实账务标识。
- 外部参考名称和开发工具署名。
- 不应进入仓库的本地协作文件和配置目录。

正常的产品需求可以讨论可选的 AI 能力，但不得包含开发过程署名、临时上下文或具体开发工具痕迹。

## 10. 异常处理

- 文档互相矛盾时，停止扩散该规则并查找最近的有效决定。
- 决定编号重复时，在提交前修正，不重新解释已经发布的编号。
- 代码行为无法由现有规则解释时，先补充决定和测试，再继续扩展实现。
- 历史资料不足时，保留未决状态，不根据推测补全事实。
- 隐私检查命中时，默认阻止提交，由维护者确认内容是否可以公开。

## 11. 验收标准

本设计落实完成时应满足：

- 九份正式文档均已建立且职责不重叠。
- `README.md` 已改为中文入口并链接所有正式文档。
- `docs/ARCHITECTURE.md` 已区分确定技术、候选技术和暂缓决定。
- `docs/CONTRIBUTING.md` 包含经过验证且可直接执行的本地命令。
- `README.md` 的快速命令与 `docs/CONTRIBUTING.md` 保持一致。
- 已确认的核心决定和账务规则已从旧资料迁入。
- `docs/CURRENT_STATE.md` 能独立说明当前进度和下一步。
- 文档检查和现有代码测试均能通过。
- 仓库历史与工作树不存在个人数据、本机信息或开发工具痕迹。
