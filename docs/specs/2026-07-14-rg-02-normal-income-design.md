# RG-02 普通收入设计

## 1. 目的

本设计冻结公开匿名黄金场景 `RG-02` 的业务答案，用于验证一笔手工普通收入从确认入账到余额、收入统计、对账和分类改名的完整闭环。

本设计使用一笔工资收入作为完整主场景，并增加红包收入和项目款收入两个相互独立的轻量变体。变体只证明不同收款账户和收入分类可以复用同一规则，不把名称本身当作自动判断收入性质的依据。

## 2. 范围

`RG-02` 覆盖：

- 手工创建一笔进入资产账户的普通收入。
- 金额、二级收入分类和收款账户的必填校验。
- 同币种分录平衡、账户余额、收入、现金流入和净资产变化。
- 无外部凭证时的分录级待对账状态。
- 同一次保存请求重试时只产生一次收入影响。
- 收入分类改名后的稳定 ID、历史显示和名称变更记录。
- 支付钱包红包和银行卡项目款两个用户已确认的普通收入变体。

`RG-02` 不覆盖退款、本人账户转账、借入资金、自动收入识别、导入解析、来源匹配、预算规则、网络、同步或智能建议。退款、转账和借贷由其他黄金场景独立验证。

## 3. 固定数据

### 3.1 公共元数据

| 项目 | 固定值 |
| --- | --- |
| 场景 ID | `RG-02` |
| 场景级别 | `core_required` |
| 规则版本 | `1` |
| 时区 | `Asia/Shanghai` |
| 币种 | `CNY` |
| 金额精度 | `2` |
| 账本 ID | `ledger-a` |

### 3.2 主场景账户与分类

| 项目 | 稳定 ID | 显示名 |
| --- | --- | --- |
| 收款资产账户 | `asset-bank-a` | 银行卡 A |
| 期初权益账户 | `equity-opening-a` | 期初权益 A |
| 一级收入分类 | `income-category-work` | 职业收入 |
| 二级收入分类 | `income-category-salary` | 工资，随后改名为薪资 |
| 隐藏收入账户 | `income-account-salary` | 工资收入 |

名称只用于显示，稳定 ID 才是交易关联和机器比较依据。二级收入分类关联隐藏收入账户，用户分类与真实金融账户保持为不同维度。

## 4. 主场景前置状态

主场景开始前存在一笔有效的期初余额交易：

| 交易 ID | 时间 | 账户 | 分录金额 |
| --- | --- | --- | ---: |
| `tx-opening-a` | `2026-01-01T00:00:00+08:00` | `asset-bank-a` | `+1000.00 CNY` |
| `tx-opening-a` | `2026-01-01T00:00:00+08:00` | `equity-opening-a` | `-1000.00 CNY` |

两条分录合计为零。工资到账前，银行卡 A 的重放余额为 `1000.00 CNY`，账本没有其他有效资金交易。

## 5. 创建工资收入

### 5.1 用户操作

用户选择手工记账并填写：

- 业务类型：收入。
- 金额：`3000.00 CNY`。
- 二级分类：`income-category-salary`，显示为“职业收入 > 工资”。
- 收款账户：`asset-bank-a`。
- 统计时间：`2026-01-16T09:00:00+08:00`。
- 付款方、备注、标签、图片和外部凭证：空。

用户执行保存即构成本次明确的人工确认。该操作没有导入候选、来源推断或自动确认。

### 5.2 正式交易

保存成功后创建一笔当前有效版本的正式交易 `tx-income-rg02`，并生成且仅生成以下两条有效分录：

| 分录 ID | 账户 | 金额 | 含义 |
| --- | --- | ---: | --- |
| `posting-bank-rg02` | `asset-bank-a` | `+3000.00 CNY` | 银行卡资产增加 |
| `posting-income-rg02` | `income-account-salary` | `-3000.00 CNY` | 工资收入增加 |

两条分录按 `CNY` 合计为零。界面只显示工资收入和银行卡到账结果，不向普通用户展示内部账户符号。

## 6. 余额与统计结果

工资交易生效后必须得到以下结果：

| 验收维度 | 预期结果 |
| --- | ---: |
| 银行卡 A 余额变化 | `+3000.00 CNY` |
| 银行卡 A 期末余额 | `4000.00 CNY` |
| `2026-01-16` 收入 | `3000.00 CNY` |
| `2026-01` 收入 | `3000.00 CNY` |
| `2026-01-16` 现金流入 | `3000.00 CNY` |
| `2026-01` 现金流入 | `3000.00 CNY` |
| 消费 | `0.00 CNY` |
| 净资产变化 | `+3000.00 CNY` |
| 预算结果 | 不适用 |

“预算结果不适用”表示场景没有预算配置，不得被解释为收入或消费为零。余额和统计必须来自同一笔当前有效交易。

## 7. 对账、证据与幂等

- 手工保存是人工确认事实，但不是外部金融凭证。
- `posting-bank-rg02` 属于真实资产账户，初始对账状态为“待对账”。
- `posting-income-rg02` 属于隐藏收入账户，不设置金融账户对账状态。
- 交易列表汇总显示“待对账”。
- 场景中不存在外部证据引用、匹配记录、推断候选或差异记录。
- 待对账状态不改变交易有效性、余额或报表结果。
- 同一次保存请求因连续点击、客户端重试或结果重放而再次提交时，只返回 `tx-income-rg02`，不创建第二笔交易、分录或收入统计。

以后出现银行流水时，可以在独立对账流程中补充证据并更新对账状态，但不得再创建一笔收入。

## 8. 分类改名

工资收入创建完成后，用户把二级分类“工资”改名为“薪资”。系统必须：

1. 保持分类 ID `income-category-salary` 不变。
2. 保留“工资 -> 薪资”的分类名称变更历史。
3. 让历史交易显示“职业收入 > 薪资”。
4. 保持交易关联的隐藏收入账户 ID 不变。
5. 不创建新的账务交易版本或资金分录。
6. 保持银行卡余额、收入、现金流入、消费、净资产和对账状态不变。

分类改名是分类资料变化，不是交易修正。只有交易自身的金额、账户、时间或分类关联发生变化时，才进入交易版本替代流程。

## 9. 轻量收入变体

两个变体分别从独立的零余额状态运行，不继承主场景或彼此的交易结果。

### 9.1 支付钱包红包

用户在 `2026-01-17T12:00:00+08:00` 手工确认一笔 `88.88 CNY` 的红包属于真实收入。固定引用为：

| 项目 | 稳定 ID | 显示名 |
| --- | --- | --- |
| 收款资产账户 | `asset-wallet-b` | 支付钱包 B |
| 一级收入分类 | `income-category-gifts` | 礼金 |
| 二级收入分类 | `income-category-red-packet` | 红包 |
| 隐藏收入账户 | `income-account-red-packet` | 红包收入 |
| 正式交易 | `tx-income-rg02-red-packet` | 红包收入 |
| 资产分录 | `posting-wallet-rg02-red-packet` | 钱包增加 |
| 收入分录 | `posting-income-rg02-red-packet` | 红包收入增加 |

预期结果为：

- 支付钱包 B 余额增加到 `88.88 CNY`。
- 收入和现金流入各增加 `88.88 CNY`。
- 消费为零，净资产增加 `88.88 CNY`。
- 资产分录与隐藏红包收入分录平衡。
- 真实钱包分录和交易汇总均为“待对账”。

### 9.2 银行卡项目款

用户在 `2026-01-18T14:00:00+08:00` 手工确认一笔 `1200.00 CNY` 的项目款属于真实收入。固定引用为：

| 项目 | 稳定 ID | 显示名 |
| --- | --- | --- |
| 收款资产账户 | `asset-bank-a` | 银行卡 A |
| 一级收入分类 | `income-category-business` | 经营收入 |
| 二级收入分类 | `income-category-project-payment` | 项目款 |
| 隐藏收入账户 | `income-account-project-payment` | 项目款收入 |
| 正式交易 | `tx-income-rg02-project-payment` | 项目款收入 |
| 资产分录 | `posting-bank-rg02-project-payment` | 银行卡增加 |
| 收入分录 | `posting-income-rg02-project-payment` | 项目款收入增加 |

该独立变体的银行卡期初余额为零，预期结果为：

- 银行卡 A 余额增加到 `1200.00 CNY`。
- 收入和现金流入各增加 `1200.00 CNY`。
- 消费为零，净资产增加 `1200.00 CNY`。
- 资产分录与隐藏项目款收入分录平衡。
- 真实银行卡分录和交易汇总均为“待对账”。

红包和项目款只有在用户明确确认其收入性质时才使用上述口径。系统不得仅凭名称把退款、本人转账、借款、代收款、报销或其他不明确来款自动归为收入；信息不足时保持待确认。

## 10. 输入校验与禁止副作用

金额必须大于零，且必须选择收款账户和可用的二级收入分类。以下输入均不得创建正式交易、分录、版本、余额变化、统计变化或对账变化：

- 金额缺失、为零或为负数。
- 收款账户缺失。
- 收入分类缺失、只选择一级分类或选择已停用分类。
- 使用支出分类作为收入分类。

`RG-02` 不得创建订单关系、退款关系、转账、借贷、消费、预算结果、导入候选、外部证据或网络与同步副作用。

## 11. 机器可比较契约

`RG-02` 沿用 `RG-01` 已建立的版本化 JSON 契约和公共校验能力：

- 精确两位十进制金额字符串。
- 稳定场景、账户、分类、交易、版本和分录 ID。
- 带时区的 ISO 8601 交易时间。
- 逐币种平衡、全场景分录 ID 唯一和账户引用校验。
- 有效分录余额重放与预期余额比较。
- 匿名数据、禁止副作用和同次请求幂等断言。

主场景冻结完整输入与结果。红包和项目款作为独立轻量变体，只冻结各自的确认输入、两条平衡分录、余额、收入、现金流入、消费、净资产和对账结果，不重复主场景的分类改名与全部输入反例。

## 12. 验收标准

`RG-02` 只有同时满足以下条件才算通过：

- 工资主场景严格包含一笔有效普通收入和两条平衡分录。
- 银行卡余额为 `4000.00 CNY`，收入与现金流入各为 `3000.00 CNY`。
- 消费为零，净资产增加 `3000.00 CNY`，预算为不适用。
- 无外部凭证时，真实收款分录和交易汇总均为待对账。
- 同一次保存请求重试不产生第二次资金或统计影响。
- 分类改名后历史显示新名称，但分类 ID、交易、余额、统计和对账不变。
- 红包与项目款变体各自产生一次独立、平衡且已由用户确认的收入结果。
- 无效输入产生零个有效资金分录和零状态变化。
- 场景在关闭网络、同步和所有可选智能能力后仍得到相同结果。
