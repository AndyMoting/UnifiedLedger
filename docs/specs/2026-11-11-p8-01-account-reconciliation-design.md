## 1. 起点：本规格要修的五条现状

1. **确认面只认转账腿**：写路径完整性谓词是 `COALESCE(tx.canonical_kind, tx.kind) = 'ACCOUNT_TRANSFER'`（`Ledger.sq:9027-9039`），其余类型返回 `P408_POSTING_NOT_ELIGIBLE`。
2. **matcher 完备但零生产消费者**：`P408Matcher.kt:119-182` 按 O-1 五字段同判、O-2 ±2 自然日成候选；多命中 `AMBIGUOUS`、无唯一命中 `UNRESOLVED`，从不自行选择（O-3）。全仓 `P408Matcher(` 的调用点都在测试里。
3. **读面资格使「待对账」只在旧腿上可达**：`isReconciliationEligible`（`LedgerEntryReadModels.kt:102-107`）要求 rg03 标记或有证据链或已有对账行。产品行只由 v23 迁移种子（`Ledger.sq:9112`、`22.sqm:143-152`）与确认/修正写入，**迁移播种只覆盖 v23 之前的存量转账腿**；`PENDING` 因此只在被种子覆盖的旧腿上可达，v23 之后新建的腿恒显示「无对账资格」。
4. **没有账户范围读，也没有「为什么匹配」读模型**：`P408ReconciliationReadPort` 只有 ledger 级一个方法（`P408Reconciliation.kt:160-162`）；`reconciliation_request_snapshot` 持有 `match_basis`/`window_days`/`natural_day_distance`/`human_decision`，但唯一读者是测试专用查询。
5. **候选证据必须先有投影，而 intake 不产投影**：matcher 的身份字段全部来自 `P408EvidenceNormalizedProjectionFacts`（`P408Matcher.kt:33-43`），`evidence_projection` 是唯一匹配权威（`D-112`）。导入 intake 只建 `import_source_record` + `import_evidence`（`SqlDelightImportSpineStore.kt:211-217`），投影只在导入确认、确认链接与修正这三条写路径上产生；`P408EvidenceProjectionPort.materialize` 至今无生产调用者。未确认的导入行因此无法进入匹配。

## 2. 首片冻结的行为

### 2.1 资格派生（修订 `D-145` §3.2.1 的读面）

读面资格改为（**只增不减**：今天已合格的腿不会因本派生变不合格）：

```
rg03 行存在 → 该行标记为真即合格、为假即不合格（费用腿照旧排除）
无 rg03 行   → 满足下方复合标记 或 已有活动证据链接/已有对账行（既有条款 (b) 原样保留）即合格
```

复合标记：

```
owned_by_user = 1 AND real_account = 1 AND kind IN ('ASSET','LIABILITY')
```

三列复合的先例见 `Rg07StateProjector.kt:223`；该行另含「排除储值账户」的**场景专属**条件（RG-07 黄金夹具口径），**产品资格不采用该排除**——`ACCOUNTING_RULES.md:188` 明写商户余额与批次证据核验储值资产分录，储值资产腿必须可对账。`active` 不参与（停用不改历史呈现，`ACCOUNTING_RULES.md:259`）；系统与外部账户由 `owned_by_user = 0` 排除，隐藏过账账户由 `kind` 排除（`ACCOUNTING_RULES.md:261`：隐藏过账账户随所属叶子分类，属费用/收入账户）。

满足资格且没有对账行时，读作 `PENDING`（待对账）。

这条只改**呈现派生**，不改写入：历史分录、金额、余额、版本、报表零变化。既无复合标记也无条款 (b) 的分录仍为「无对账资格」，`null` 仍表示「不显示任何对账状态」。

写面资格本片不动——`confirmLink` 继续只接受 `ACCOUNT_TRANSFER` 腿。**状态与动作分开呈现**：一条腿可以如实是「待对账」而在当前版本里「暂不支持在应用内核对」。

### 2.2 入口（两处，同一用例）

- **入口 A（账户视角）**：账户流水屏新增「账户对账」动作，进入该账户的对账队列。
- **入口 B（候选视角）**：导入审核的候选行在未链接时提供「用于核对既有分录」，进入同一屏的**证据聚焦模式**（以该候选的证据为锚，列可确认的分录）。

两个入口共用同一绑定、确认与审计用例及同一呈现组件；区别只在初始查询方向。

### 2.3 队列

队列 = 该账户当前有效、满足 §2.1 复合标记的分录，按 `occurred_at DESC, posting_id ASC` 键集分页（页大小 100）。每行呈现：日期、备注或交易类型、该腿精确带符号金额与币种、五态状态。

- 队列列未核对分录；已核对分录收在独立分区、默认折叠、按需展开。
- 汇总按 `(币种, 状态)` 聚合：**已核对合计 / 未核对合计 / 条数**。禁止呈现「账户余额 − 区间明细合计」的差额——该算法已被竞品语料自我否定（`UL_ABSORB_2026-11-03.md:106` E2），且余额不得由对账反推。
- 聚合读失败或金额溢出时显式失败并保留已加载行，不以零掩盖。

### 2.4 证据绑定与候选

候选证据必须是 `READY` 投影行。未投影的导入证据进入队列前要先完成一次**绑定**：用户明确「这条导入行属于此账户」，应用层据该决定调用 `P408EvidenceProjectionPort.materialize(...)`（目标账户 = 该腿账户，币种与精度取该账户目录值）。

- 投影内容不可变，当前权威行只能由既有修正路径取代（`supersedeP408EvidenceProjection`），应用内不提供改绑或解绑入口（`P408EvidenceProjectionPort.kt:3-12`）。界面必须在动作前写明「绑定后不能在应用内改绑」，不得默认替用户绑定，也不得在浏览时静默物化。
- 绑定是**登记的派生写**：只写 `evidence_projection`，零账务效果（不建交易、不建分录、不改余额、不改报表）。同参数重放命中 `NoChange`，零新行；`P408ProjectionState.REJECTED` 的证据进不了候选，界面如实说明拒绝码。
- 绑定可用后，应用层以冻结的 matcher 计算候选：`match(evidence, [该账户在当前版本内、±2 自然日窗内的可对账分录])`，只取该腿出现在候选集内的结果。matcher 未被修改，也不在此处重新实现匹配。

呈现规则：

- 同腿多条可用证据按**解析后的瞬时**升序呈现（来源时间取 `import_source_record.occurred_at`，解析后比较），不可解析者置末，同值以 `evidence_id` 升序；每条各自给出处置与自然日距离。不按原始文本排序——原始时间串可带偏移量，`TEXT` 升序不是时间序。
- `PROPOSED_MATCH` → 展示唯一候选，可直接确认（可确认职责由该腿方向唯一确定，见 §2.5）。
- `AMBIGUOUS` → 列出全部候选与各自距离，要求用户**明确选择**其中一条；用户选择即是 O-3 的人工决定。
- `UNRESOLVED` → 呈现成因（`no_unique_funding_candidate` / `source_time_unresolved` / `funding_facts_unresolved` 原样转述），该腿保持待对账，**零写入**。
- 该腿已有同职责活动链接时，其余同职责证据一律呈现为不可确认（对应既有 `P408_POSTING_RESPONSIBILITY_ALREADY_LINKED`）。
- §2.3 中不可确认的腿不进入候选计算；匹配依据只呈现冻结五字段与自然日距离，`confidence` 只有 `EXACT`，界面不得暗示评分或排序。

### 2.5 确认

确认是两步：先看清四要素（外部证据、证据职责、匹配依据、人工决定），再点确认。

- **职责按方向唯一裁定**：`out`（负向）腿 = `REAL_ACCOUNT_POSTING`，`in`（正向）腿 = `DESTINATION_ASSET_POSTING`（`SqlDelightP408ReconciliationStore.kt:170-183`；O-5 对同一笔转账的两条腿分别冻结这两种职责）。一笔转账的两条腿因此都可确认、各自独立对账；界面按该腿方向给出唯一职责，不让用户自选。
- 请求由应用层构造 `P408ConfirmLinkRequest`，`basisVersion = 2`、`windowDays = 2`、`naturalDayDistance` 取 matcher 输出、`matchBasis` 取冻结五元组、`confirmedAt` 取注入时钟、身份由账本既有发号端口给出。**界面不得自造 basis 或距离**。
- 结果按类型化三分支：`Accepted` → 刷新队列、汇总与详情；`NoChange` → 视为成功且不重复写；`Rejected(code)` → 原样呈现 code 对应的可读文案，零写入。
- **结果未知**（进程中断、无回执）：界面提示「结果未知，重新进入核对」，重进后以权威回读判定。同一 requestId 重试要么命中 `NoChange`＋原回执（此前已提交），要么重新执行得到等价结果（此前已回滚）——两种都不得产生第二行链接。

### 2.6 审计回看

对已核对腿展示：证据来源（哪一次导入、哪条来源行）、证据职责、匹配依据五字段与自然日距离、人工决定时间，以及状态历史（`confirmed`/`posting_replaced`/`corrected` 与序号）。

历史与依据**只读**；没有任何界面路径可以改写或删除既有链接。

### 2.7 双记账防护

证据被链接到既有分录后，同一证据不得再产生第二笔正式交易：

- 导入审核列表不落新状态，由 `evidence_link` 是否存在**派生**显示「已用于核对既有分录」。
- 导入确认路径新增前置守卫：候选所属证据已有活动链接时类型化拒绝 `IMPORT_EVIDENCE_ALREADY_RECONCILED`，零正式写入、零候选状态变化（`import_candidate` 状态行与 `import_candidate_status_history` 均零增）。
- 同一证据再次确认对账由既有 `P408_EVIDENCE_ALREADY_LINKED` 拒绝；同一分录同职责再次链接由 `P408_POSTING_RESPONSIBILITY_ALREADY_LINKED` 拒绝。

## 3. 读写契约（零 DDL）

| 用途 | 形态 | 说明 |
| --- | --- | --- |
| 队列 | 具名查询 + 端口方法 | 账户 + 键集游标；返回该腿当前状态、是否有活动链接、交易类型、账户复合标记 |
| 汇总 | 具名查询 + 端口方法 | 账户 × (币种, 状态) 合计与条数 |
| 待绑定证据 | 具名查询 + 端口方法 | 账户 + 时间窗；只取尚无 `READY` 投影、且未链接的导入证据，携带原始时间事实与候选身份 |
| 候选 | 既有 matcher（纯函数） | 输入只取 `READY` 投影；应用层新增用例，不复制匹配规则 |
| 绑定 | 既有端口 `materialize` | 首个生产调用点；登记为派生写，零账务效果 |
| 确认 | 既有端口 `confirmLink` | `basisVersion = 2`；不新增写路径 |
| 审计 | 具名查询 + 端口方法 | 分录 → 请求快照依据字段 + 链接行 + 状态历史 |
| 详情腿投影 | 既有查询增列 | 增 §2.1 复合标记的三个源列 |

所有只读查询的有效交易谓词复用 `transaction_effective_state`（`D-156` 冻结的唯一 SQL 定义点），不另写一份。全片唯一的写动作是 `materialize`（派生）与 `confirmLink`（对账面），均无余额/报表效果。

## 5. 范围边界

**本片不做**（不得据本规格实施）：写路径扩面到非 `ACCOUNT_TRANSFER` 分录（属 P8-01b，需 v36→v37 回填与谓词放宽）；`DIFFERENCE`/`MISSING` 的用户可写声明（今天只有修正路径能写这两个状态，首片只解释成因）；时间范围选择器；批量确认；跨账户或跨币种匹配；`PARTIAL` 的写入（产品中无写入者，保持只读呈现）；绑定后改绑或解绑（投影是不可逆终态，改绑属另一决策面）。

**不变量**：正式金额、分录、余额、报表、版本、作废恢复零变化；对账状态只描述核验程度；不伪造交易补平差额；不把通道总额或余额差额当作对账结论。

**P8-01b 的登记范围**（本规格不实施）：`selectP408PostingIntegrity` 放宽为真实资产/负债分录、`posting_reconciliation` 回填迁移、非转账类型上的证据职责裁定、届时对读面的统一。
