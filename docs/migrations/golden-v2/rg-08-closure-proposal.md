## D-084 "44-operation" Disposal

The frozen fixture `golden/rules/rg-08.json` was independently counted for this proposal. It contains exactly 44 operation-shaped cases: 32 v1 operations plus 12 idempotency retries.

| Directory | Count | Entries |
| --- | --- | --- |
| `lend` | 1 | lend |
| `manual_collection` | 1 | manual collection |
| `principal_cap` | 2 | `maximum_valid_collection` (accepted allocate), `over_balance_attempt` (rejected) |
| `import_collection` | 9 | `candidate` 1, `incomplete_confirmations` 6, `confirmation` 1, `mirror_evidence` 1 |
| `counterparty_identity.rename` | 1 | rename (zero effect) |
| `invalid_inputs` | 18 | 16 unique predicates |
| `idempotency.retries` | 12 | 6 request anchors + 6 source anchors |
| **Total** | **44** | 32 v1 + 12 retry |

The remaining top-level material is not operation-shaped: `canonical_states` (6 state snapshots), `operation_baselines` (14 baseline snapshots), plus `opening`, `catalog`, `behavior_codes`, `evidence_policy`, `entity_registry`, `out_of_scope` and `forbidden_side_effects`. The string `pre_operation_baseline` occurs 38 times in the fixture as an inline full-state snapshot key inside operation documents; it is document material, not an operation count, and the 38 occurrences must not be mistaken for case counts.

D-084 approves a "44-operation" oracle. Unlike D-083's "50-operation" (which exceeded the frozen RG-10 fixture), 44 is the frozen RG-08 fixture's own operation-shaped count, so the oracle is implemented as a strict 1:1 mirror of the 44 frozen cases (RG-09/RG-10 precedent: id-for-id, no completion logic, no synthetic expansion, no fixture rewrite).

The accepted 6 / rejected 25 / no_change 13 split is a runtime mapping decision declared here explicitly. Accepted 6 = 5 formal (lend, manual-collection, cap-maximum, confirm-import, mirror-evidence) + 1 intake (import-candidate, zero formal effect by design). Rejected 25 = `over_balance_attempt` 1 + `incomplete_confirmations` 6 + `invalid_inputs` 18. No_change 13 = rename 1 + retries 12. None of the 12 frozen retry blocks carries an `accepted: true`-style first-time marker (verified against the frozen fixture: all twelve publish only `duplicate_counts`/`formal_effect_counts`/`resulting_state`/`returned_stable_ids`), so the retry classification comes from the input anchor alone (Classification Inference Registry rule 1); the runtime maps an identical-fingerprint replay to `NoChange` returning the first-time IDs (D-084 retry equality), and the oracle asserts both the no-change status and the first-time IDs.

## v2 Projection Registry

The oracle is an independent replay comparator, not a fixture-to-runtime identity copier. It registers the following v2 projections, confined to the comparison layer and never altering runtime provenance, formal ownership, or append-only rows. The registry is taken from the `Rg08FullStateOracleTest` class contract and the `Rg08FixtureReplay` adapter contract.

1. **Fixed-offset time rendering.** The runtime stores absolute instants; the frozen v1 shapes render them in the case timezone (Asia/Shanghai, fixed +08:00), so every instant is projected through the fixed-offset formatter (`SHANGHAI_INSTANT_FORMAT`).
2. **Mirror/merge typed audit-link projection.** Mirror/merge references are typed audit links in the runtime (RG08-GAP-03: they are never evidence-link fields); the frozen v1 shape carries `mirror_of_evidence_id`/`merged_into_evidence_link_id` on the merged evidence link, and the projection translates the runtime audit links back onto the link (`projectEvidenceLink`).
3. **Balances publish only frozen keys.** Frozen v1 states publish balances only for the lending-story accounts; zero-balance accounts outside the published set (`asset-external-c`, `expense-validation`) are omitted the same way by the projection (`projectBalances`).
4. **Rejected field-path mirror.** Rejected field paths are asserted from an oracle-side mirror of the runtime rejection table (RG-10 precedent). Two frozen v1 `field` names do not project 1:1 onto the runtime normalized paths and are documented in `expectedFieldPath`: `negative-interest` (v1 `interest_amount`; the runtime normalizes nonnegativity to the principal field) and `guessed-split` (v1 `components`; the runtime reports the split-source field).
5. **No-owner declarations are not asserted.** The frozen `candidate_status` markers, the `guessed_*`/`fallback_event_type` nulls, and the v1 `expected_interest_metadata` interest/accrual numbers are v1-era declarations without a runtime owner (accrual interest is out of scope); zero formal effect is asserted through the effect counts and the before/after state equality instead. The `expected_interest_metadata` income/net-worth numbers project through the report delta only.
6. **Explicit-confirmation projection.** The frozen requests express confirmation via `confirmation_mode` (`explicit_manual_save`) or the six `explicitly_confirmed_fields`; the runtime requires the explicit boolean, which is projected as true on those paths (RG08-GAP-03/04).
7. **Intake proposed-facts projection.** The imported candidate's proposed facts are projected from the frozen bank credit source record (amount to proposed total, account to proposed destination, `value_at` to proposed actual receipt time); the agreement source is the second intake source (RG08-GAP-03).
8. **Catalog display-name override.** The frozen catalog carries the post-rename display name (the fixture's final state); the runtime input file supplies the pre-rename name so the rename operation stays replayable.
9. **Synthetic commit ids are inert.** The frozen `principal_cap.over_balance_attempt` and the invalid inputs carry no runtime commit ids; ids are synthesized deterministically (`*-over-balance-rg08` convention) and stay inert because those paths reject before any state mutation.
10. **Per-entity comparison by id.** Entity arrays are compared per entity by id and only over the fields the frozen v1 entity publishes (runtime-only extra fields are not part of the v1 publication, RG-10 rule-3 precedent applied per entity); the entity count is still exact, so a runtime entity the frozen state does not have (or vice versa) fails loudly (`assertJsonEquals`).
11. **Reconciliation needs no projection.** The runtime emits the frozen reconciliation key shape verbatim — posting-level keys (`not_applicable`/`matched`/`pending`) plus a transaction-level key (`complete`/`pending`) per lending transaction — so the projection copies the runtime map key for key (`projectState` reconciliation entry).
12. **Confirm-import provenance projection.** The frozen provenance block (`source_ids`, `candidate_id`, `confirmation_request_id`, `rule_version`, `confidence`, `original_source_payload_hash`) is asserted from the runtime confirmation, candidate and source state (`assertExpectedSpecifics`).

Additional registered projection detail: `mirror_evidence` publishes flat top-level counts, some without the `new_` prefix; the oracle asserts every flat count key that exists in the runtime counts map directly.

## Classification Inference Registry

The fixture adapter classifies every operation with the following chain (`Rg08FixtureReplay.fixtureOperation`):

1. a retry source id => `no_change` (generic `retry_idempotent_input`);
2. explicit `expected.accepted: true` => `accepted`;
3. explicit `expected.accepted: false` => `rejected`;
4. `expected.resulting_state` present without `effect_counts` => `accepted` (the intake/confirm/mirror blocks carry a resulting state but no effect counts);
5. otherwise => `no_change`.

Two inferences are registered here explicitly. `counterparty_identity.rename` carries no `accepted` field; it is classified `no_change` per D-084 (no_change 13 = rename 1 + retries 12) even though the runtime returns `Accepted` with zero effect on the frozen shape and returns the counterparty/name-history ids — asserted in `assertOutcome`'s rename branch. The 12 retries are classified `no_change` through rule 1 regardless of the first-time markers the fixture carries on some retry blocks, because the runtime maps an identical-fingerprint replay to `NoChange` with the first-time IDs (D-084 retry equality). The generic `retry_idempotent_input` expression of the 12 frozen retries is the D-084 ruling and is an explicit deviation from D-083's "retry keeps the original action" rule; D-084 records that the RG-08 frozen fixture semantics win and that the deviation rationale is recorded. This proposal records the chain so that a future operation missing all markers is not silently misclassified; the adapter comment should be treated as the classifier contract until a stricter schema-side outcome declaration exists.

## Runtime Deviation Register

Registered deviations and their disposition. DEV-01 received the parent ruling recorded below; DEV-02/03 are fix-recorded runtime decisions mirrored by the oracle.

- **RG08-DEV-01 (ruled, authorized by the parent agent).** The runtime derives the manual bank-credit source's account anchor from the destination account (`Rg08Operations.bookCollection` sets the credit source `account_id` to the destination account id); the frozen v1 manual credit source carries no account anchor, while the import credit keeps its explicit one. **已裁决：destination-account 推导经主代理授权（2026-08-09，冻结案例推导值==输入锚点）** — the derived value equals the frozen case's input anchor (`asset-wallet-b`), so the derivation is closed as correct behavior and no further mapping authority is required. The deviation is asserted explicitly in `Rg08FullStateOracleTest.assertExpectedSpecifics` (the state projection renders only the v1 published fields, so the derivation would otherwise be invisible).
- **RG08-DEV-02 (fixed in runtime, oracle mirror aligned).** `bookCollection`'s destination-evidence branch now fires only on the imported path, where the credit branch did not run and the link joins the pending candidate's bank credit source/evidence to the destination posting. On the manual path the credit branch already created the identical destination link (`evidence-link-rg08-manual-credit`), so the branch no longer fires a duplicate with the same id; the frozen manual state's `evidence_links` are matched exactly.
- **RG08-DEV-03 (fixed in runtime, oracle mirror aligned).** `AllocateLendingCollection` returns the frozen stable ids `{transaction_id, version_id, settlement_id, position_id}` per the `retry-rg08-request-cap-maximum` `returned_stable_ids` contract, not the request id; `expectedReturnedIds` in the oracle mirrors that contract.
- **Anchor-style retries.** Twelve frozen retries resolve inside a single in-memory runtime session: six anchor on request ids (the original operation's own identity) and six anchor on source ids. Of the six source anchors, four are registered as explicit anchor receipts (`Rg08Operations.registerAnchorReceipts`: lend debit source, manual confirmation source, manual credit source, agreement source) and two replay through the original operation's own identity receipt (the import credit is the intake identity, the import mirror is the merge identity). The store has no anchor-receipt persistence path, so the oracle drives a pure `Rg08Runtime` with no store (RG-10 precedent), and the persistence design for anchor retries stays open (see Unclosed Items).

## Persistence

`14.sqm` implements the additive v14 to v15 migration (D-084, aligned with the RG-10 additive pattern): existing formal rows and all prior RG owners remain untouched. It creates 20 RG-08-exclusive tables and 56 triggers:

- **Tables (20):** `rg08_operation`, `rg08_returned_id`, `rg08_position`, `rg08_position_history`, `rg08_settlement`, `rg08_settlement_component`, `rg08_settlement_history`, `rg08_candidate`, `rg08_candidate_status_history`, `rg08_source_record`, `rg08_candidate_source`, `rg08_confirmation`, `rg08_evidence`, `rg08_evidence_link`, `rg08_audit_link`, `rg08_posting_semantic`, `rg08_posting_reconciliation`, `rg08_reconciliation_history`, `rg08_formal_transaction_metadata`, `rg08_name_history`.
- **Trigger families (56):** immutable update/delete guards per owner; append-only sequence guards (position/settlement/candidate/name/reconciliation histories); position history direction guard; candidate lifecycle guard (only `PENDING_CONFIRMATION` to `CONFIRMED` with confirmed proposed facts); formal-owner guards (`rg08_settlement` onto `COLLECT` transactions, confirmation targets onto `LEND`/`COLLECT`, posting semantics onto LEND/COLLECT postings); typed audit-link target guard (evidence ids never mix with evidence-link ids, RG08-GAP-03); evidence-link target/lineage guards (typed edges, never free-form labels); reconciliation current/transition guards (`PENDING` to `MATCHED` with a matching history row and evidence link); evidence-type guard (evidence subtypes are typed derivations of their source kind); source mirror guards (a mirror source always references a different origin).

Formal transactions continue through the shared chain (`ledger_transaction`, `posting_set`, `posting` owners). `SqlDelightRg08Store.persistFormalRecord` inserts `TransactionKind.name` (`LEND`/`COLLECT`) into the shared `ledger_transaction.kind`; canonical kind reads use `COALESCE(canonical_kind, kind)`, and `versionFifteenWiresLendCollectCanonicalKindsAndProtectsRg08Guards` asserts LEND/COLLECT canonical kinds survive write and reopen. Successful operations commit in one `database.transactionWithResult`; failures roll back with the baseline intact (D-084). Migration DDL atomicity is a caller contract: the v14→v15 DDL is atomic only when the caller wraps `Schema.migrate` in a transaction (the failure test `versionFourteenToFifteenDdlFailureRollsBackEveryRg08Owner` exercises exactly that transactional path — `LedgerDatabase(driver).transaction { Schema.migrate(driver, 14, 15) }` — so production wiring must wrap every `Schema.migrate` call the same way; RG08-SPEC-009 / RG08-QA-07). Schema version is asserted 15 in `LedgerDatabaseMigrationTest` (`freshSchemaCreatesEveryLedgerDataTableAtVersionFifteen`, `versionFourteenToFifteenPreservesFormalRowsAndCreatesEmptyRg08OwnersAcrossReopen`, `versionFourteenToFifteenDdlFailureRollsBackEveryRg08Owner`, `versionFifteenWiresLendCollectCanonicalKindsAndProtectsRg08Guards`, `freshVersionFifteenAndMigratedVersionOneHaveEquivalentSchemaMetadata`) and bumped in the 7 existing schema-version test files listed in Scope And Approval. `minSdk = 34` is declared in the ledger-data build (RG-09 v14 decision continuation).

## Known Records

- `loadPersistedSnapshot` hard-errors on a ledger transaction without `rg08_formal_transaction_metadata` (`missing persisted RG-08 formal transaction metadata`); the RG-08 store shares this shared-formal-chain limitation with the RG-09/RG-10 stores.
- The store hard-errors on a persisted operation still `PENDING` and refuses to finalize `RequestIdentityConflict` (`cannot finalize identity conflict`): identity conflicts exist only inside the in-memory runtime session, and the persisted `rg08_operation.outcome` guard admits only `PENDING` to `ACCEPTED`/`NO_CHANGE`/`REJECTED`.
- Imports never auto-confirm: `IngestImportedCollectionCandidate` keeps candidates `pending_confirmation` with zero formal effect until `ConfirmImportedCollection` with all six explicitly confirmed fields; this is the frozen v1 semantics, asserted by the oracle import-path family.
- The rename zero-effect no-change classification and the allocate returned-stable-ids contract are inferences (see Classification Inference Registry and RG08-DEV-03) and are asserted by the oracle.
- **Rename persistence contract (RG08-SPEC-007).** The runtime accepts the rename and the store persists it as an `ACCEPTED` outcome (with the counterparty/name-history returned ids and the `rg08_name_history` append); the frozen classification is `no_change` (D-084 count 13 = rename 1 + retries 12). This is an explicit persistence contract: `ACCEPTED` is the runtime/persistence outcome, `no_change` is the frozen v1 classification; downstream consumers of the persisted `rg08_operation.outcome` must consume the `ACCEPTED` semantics (zero formal/intake effect, name-history append) and must not re-derive the frozen classification from the persisted outcome.
- `expected_interest_metadata` interest/accrual numbers are v1 informational with no runtime owner (projection rule 5); accrual interest is out of scope.

## Fallback 再评估记录（D-088 强制条款，2026-08-10）

1. **序列化证据口径。** 对冻结契约 `golden/rules/rg-08.json` 全文件递归复算：139 个同时包含 `occurred_at` 与 `statistics_at` 的序列化交易快照中，139 / 139 两字段相等；这些重复快照对应 5 个唯一的 transaction/current-version 对。全文件字段出现次数为 `occurred_at=364`、`statistics_at=139`、`effective_at=0`。`effective_at` 缺席本身只说明冻结序列化形状未发布该字段，不能单独证明第三时间已折叠。
2. **第三时间的独立实现证据。** `Rg08FixtureReplay.kt` 对 opening transaction 构造 `TransactionTimes(occurredAt, occurredAt, occurredAt)`；`Rg08Operations.kt` 对 lend 构造 `TransactionTimes(input.actualAt, input.actualAt, input.actualAt)`，对 manual collection、allocated collection 与 confirmed import 共用的 collect 构造则使用 `TransactionTimes(actualReceiptAt, actualReceiptAt, actualReceiptAt)`。因此当前 RG-08 runtime 的 occurred/statistics/effective 三个 instant 由构造路径明确相等，而不是从 `effective_at` 缺席推断相等。
3. **两处 fallback 边界。** Persistence 路径 `SqlDelightRg08Store.kt` 在 `record.statisticsAtText` 缺失时写入 `formal.versions.last().times.statisticsAt`；report 路径 `Rg08Operations.kt` 则调用 current-version helper，按 `transaction.currentVersionId` 选择该版本的 `times.statisticsAt`。当前 opening、lend 与 collect 构造均为每交易单版本，冻结契约的 139 个快照也只覆盖上述 5 个唯一 transaction/current-version 对，所以两种选取在当前范围内指向同一版本。Opening 的 `statisticsAtText` 为 null，触发 persistence fallback；report 会排除 opening，而 lend/collect（包括 confirm-import collect）均提供显式 `statisticsAtText`，故冻结 report 路径不触发 fallback。
4. **结论与授权边界。** 上述序列化复算与 runtime 构造证据共同满足 D-088 的 publication 前强制再评估，RG08-001 方案 (b) 的当前前提成立，可继续 D-089 已授权的 RG-08 B 批后续实现与验收。本记录不执行 publication，不授权 push，也不新增或预批准 schema migration。
5. **前提失效处置。** 若未来出现 `statistics_at != occurred_at`、runtime 的 effective time 与 occurred/statistics time 分离、可报告交易缺失 `statisticsAtText`，或多版本使 `versions.last()` 与 `currentVersionId` 不再等价，必须停止 RG-08 publication，并重新进入产品语义与 migration 决策门后再继续。新增显式 `statisticsAtText` 列只能作为该决策门中的候选方案；本记录不预先批准该列、迁移边或任何数据重写。
