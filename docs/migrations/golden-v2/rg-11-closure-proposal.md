# RG-11 Golden Schema v2 Closure Proposal

状态：active

## Authority And Boundary

This proposal records the D-085 closure candidate for RG-11 (periodic allocation + `correct_transaction_version` with the `statistics_time` semantics). RG-11 is a direct-v2 scenario: the frozen contract `golden/rules/rg-11.json` (contract_version 2.0.0, approved at commit `efbb13a`) has no v1 mapping and no adapter by design, so there is no mapping gate; per D-085:1115 the closure gate status is recorded in this proposal's review disposition. D-085 approves the complete Kotlin runtime, the 22-operation fixture oracle, and the formal SQLDelight persistence with the additive v15 to v16 schema migration, plus the two new `TransactionKind` values `PREPAID_PURCHASE` and `PREPAID_RECOGNITION` and the shared `appendVersion` domain primitive (generalizing the RG-01 `replaceNote`). Business semantics remain governed by the design document `docs/specs/2026-07-18-rg-11-periodic-allocation-design.md` and the frozen Python semantics (`test_rg11_golden_v2.py`, 11 tests). This artifact records the implemented owners, the v2 compatibility projections, the classification and runtime-deviation decisions, and the proofs required before the closure gate is marked `approved`. It does not edit the frozen `golden/rules/rg-11.json`, `.external/`, or a publication target, and it renews no push authorization (D-085:1117: push was authorized once by the user and is executed only on user instruction). RG-12 (`posting_facts` extension) opens only after this closure is complete and merged (D-085 serial constraint).

## D-085 "22-operation" Disposal

The frozen fixture `golden/rules/rg-11.json` was independently counted for this proposal (the oracle's raw-operation-registry test asserts the same counts). It contains exactly 22 operation-shaped cases across three roots, and the oracle is implemented as a strict 1:1 mirror of those 22 cases (D-084 precedent: id-for-id, no completion logic, no synthetic expansion, no fixture rewrite).

| Root | Count | Entries |
| --- | --- | --- |
| `root-main` | 6 | `main-create` (accepted), `main-recognize-01` (accepted), `main-recognize-02` (accepted), `main-recognize-03` (accepted), `main-correct` (accepted), `main-replay` (no_change) |
| `root-revision` | 6 | `revision-create` (accepted), `revision-recognize-01` (accepted), `revision-revise` (accepted), `revision-recognize-04` (accepted), `revision-recognize-05` (accepted), `revision-recognize-06` (accepted) |
| `root-z-rejections` | 10 | `operation-reject-malformed-amount`, `operation-reject-zero-amount`, `operation-reject-negative-amount`, `operation-reject-unsupported-currency`, `operation-reject-mismatched-currency`, `operation-reject-invalid-anchor`, `operation-reject-already-recognized`, `operation-reject-exceeds-prepaid`, `operation-reject-invalid-boundary`, `operation-reject-invalid-count` (all rejected) |
| **Total** | **22** | accepted 11 (5 main + 6 revision) / no_change 1 / rejected 10 |

The accepted 11 / no_change 1 / rejected 10 split is read directly from the frozen `outcome.status` blocks (the direct-v2 contract carries explicit outcomes, unlike RG-08's inference chain). The 10 rejections cover 9 unique frozen reason codes (`must_be_positive` fires twice: zero-amount and negative-amount). The rejection root's baseline carries the three seed transactions `opening` + `purchase` + `recognition-01` (rehydrated verbatim from the frozen initial state; balances, reports, reconciliation and derived statuses are recomputed by the runtime and never seeded). The single no_change op is `main-replay` with the frozen `idempotent_replay` reason code; its `returned_ids` equal the first-time ids of `main-recognize-03`, and retry equality is asserted (Classification Inference Registry).

## v2 Projection Registry

The oracle is an independent replay comparator, not a fixture-to-runtime identity copier. The registry is taken from the `Rg11FullStateOracleTest` class contract and the `Rg11FixtureReplay` adapter contract and is confined to the comparison layer, never altering runtime provenance, formal ownership, or append-only rows.

1. **Id anchors never read expected backwards.** Every frozen entity id (`main-purchase`, `main-purchase-v1`, `main-purchase-postings`, `main-purchase-cash`, `main-purchase-prepaid`, `schedule-main`, `main-revision-01`, `main-installment-01..03`, `main-recognition-link-01`, `main-correct-confirmation`, ...) is explicit in the frozen states and deltas; the runtime consumes it through the per-request anchors of `tests/fixtures/rg11-runtime-input.json` (never reverse-read from the expected result states), with `installment_ids` arrays anchored as JSON arrays. The catalog is static input no RG-11 action mutates: the domain `Account`/`Category` carry no display `name`, `reconciliation_eligible` or `hidden` fields, so the per-state catalog is asserted separately on the representable fields (id/kind/currency/owned_by_user/real_account for accounts; id/parent_id/posting_account_id/active for categories) and excluded from the per-state collection comparison.
2. **Reconciliation id assembly.** Frozen `posting_reconciliations` ids follow no uniform derivation rule (`main-opening-reconciliation` drops the `-cash` suffix, `main-purchase-cash-reconciliation` keeps it), so the fixture case exposes a postingId -> reconciliationId map assembled from the initial states' `posting_reconciliations` (input-side seeds) plus the per-request `reconciliation_id` anchors of the runtime-input file (created postings).
3. **Correct ids are operation-anchored.** The frozen `correct_transaction_version` confirmation owns the operation id itself (`operation_id == operation["id"]`, i.e. `main-correct`, not the request id), and the frozen input carries no confirmation time; the runtime-input `times` section supplies the `confirmation_created_at` anchor (`2026-02-01T00:01:00+08:00`).
4. **Rejected chain shared request id, lazily synthesized.** Six of the ten rejections (the create branch) share one frozen `request_id` (`reject-request`); the runtime rejects a second commit with the same identity and a different fingerprint (`RequestIdentityConflict`), so the shared rejections are replayed under per-operation synthesized request ids (`<operation-id>-request`). The frozen `attempted_input.request_id` is not part of any frozen output state, so the projection is inert (RG-08 invalid-inputs precedent). The four remaining rejections keep their frozen unique request ids.
5. **Fixed +08:00 time rendering.** Times render in the case timezone `Asia/Shanghai` with a fixed-offset formatter (`SHANGHAI_INSTANT_FORMAT`, `ZoneOffset.ofHours(8)`); `kotlin.time.Instant` renders UTC, so the projection recovers the frozen strings byte for byte.
6. **Balances order is not contractual.** The runtime emits the catalog order while frozen result states sort by account id; the validator compares balances as maps, so the per-state balances comparison normalizes to a set of entries. The delta `balances` value changes stay compared in the frozen sorted-by-key order (the Python test demands that order).
7. **Reports are single-currency (CNY).** The runtime report registry is currency-agnostic, so the projection pins the frozen case currency CNY on every metric.
8. **Entry order is not contractual for set-iterated collections.** Entity change id lists and balance value changes are compared in the frozen sorted order; report/derived-status value changes and status changes entry order follows the Python generator's set iteration and is not contractual, so those three are compared as sets of canonical JSON entries (mirroring `test_rg11_golden_v2.py`).
9. **Explicit null completion.** The frozen contract writes absent sides as explicit nulls; the projection does the same for `recognized_through` (revision boundary), the before/after sides of status changes, report value changes and derived-status value changes, and the `confirmation_id` of version rows.

## Classification Inference Registry

The direct-v2 fixture carries explicit `outcome.status` blocks, so every operation is classified by its frozen outcome directly; the following inferences are registered for the parts the fixture leaves implicit:

1. **Retry (main-replay) is `no_change` with the first-time ids.** The replay chain is derived from the input request ids (`firstRequestOwners` in `adaptRg11Fixture`): `main-replay` carries the same request id as `main-recognize-03` and is classified `retryOf = main-recognize-03`. The runtime maps an identical-fingerprint replay to `NoChange` returning the first-time ids (D-085 retry equality, asserted in `idempotent replay returns no change with first-time ids`). The store replays a persisted `ACCEPTED`/`NO_CHANGE` receipt the same way (`replayOutcome`).
2. **`correct_transaction_version` `statistics_time` semantics.** The corrected version v2 is appended to the target `PREPAID_RECOGNITION` transaction through the shared posting set (no new posting set, no new postings), `version_number` advances to 2, the old version v1 keeps its times and stays immutable, and an `explicit_operation_confirmation` is created with `operation_id == main-correct` (the operation id, not the request id), subject `{kind: operation, id: main-correct}` and empty payload. Balances and reconciliation state are untouched by the correction.
3. **Recognition state is audit-link derived.** A recognized installment is defined exclusively by a `periodic_allocation_recognition` audit link (from `domain_entity` installment to `transaction`); the domain payloads never carry confirmation state, and recognition results are never written back (design doc lines 10-11). `recognizedAmountMinor` and the derived statuses consume the same link set.
4. **Non-mutating outcomes keep the baseline byte identical.** Every rejected and no-change operation preserves the baseline state field by field and has zero formal effect; the oracle asserts projected baseline/result equality and frozen baseline/result payload equality (`rejected and replayed operations keep baseline and result byte identical`).
5. **Rejection predicates are fixture-anchored (op id -> predicate).** The frozen contract carries no predicate on the ten `operation-reject-*` operations, so `Rg11FixtureReplay.rejectionPredicate` (op id -> closed `Rg11InvalidPredicate`, `Rg11FixtureReplay.kt` rejectionPredicate) assigns each operation id exactly one predicate, and `Rg11Operations.rejectInvalidInput` (the closed predicate -> (reason, field path) table, `Rg11Operations.kt` rejectInvalidInput) recomputes the frozen rejection output:

   | Frozen op id | Assigned predicate | Rejected reason / field path |
   | --- | --- | --- |
   | `operation-reject-malformed-amount` | `EXACT_DECIMAL_AMOUNT` | `exact_decimal_string_required` / `$.attempted_input.amount` |
   | `operation-reject-zero-amount` | `ZERO_OR_NEGATIVE_AMOUNT` | `must_be_positive` / `$.attempted_input.amount` |
   | `operation-reject-negative-amount` | `ZERO_OR_NEGATIVE_AMOUNT` | `must_be_positive` / `$.attempted_input.amount` |
   | `operation-reject-unsupported-currency` | `UNSUPPORTED_CURRENCY` | `unsupported_currency` / `$.attempted_input.currency` |
   | `operation-reject-mismatched-currency` | `CURRENCY_MISMATCH` | `currency_mismatch` / `$.attempted_input.currency` |
   | `operation-reject-invalid-anchor` | `INVALID_ANCHOR` | `invalid_anchor` / `$.attempted_input.anchor` |
   | `operation-reject-already-recognized` | `INSTALLMENT_NOT_PENDING` | `installment_not_pending` / `$.attempted_input.installment_id` |
   | `operation-reject-exceeds-prepaid` | `EXCEEDS_REMAINING_PREPAID` | `exceeds_remaining_prepaid` / `$.attempted_input.amount` |
   | `operation-reject-invalid-boundary` | `INVALID_REVISION_BOUNDARY` | `invalid_revision_boundary` / `$.attempted_input.recognized_through` |
   | `operation-reject-invalid-count` | `INVALID_REMAINING_INSTALLMENT_COUNT` | `invalid_installment_count` / `$.attempted_input.remaining_installment_count` |

   The assignment was compared by hand against the stable rejection priority of the v2 validator (`tools/python/golden_cases/v2.py` `_periodic_allocation_rejection`) and agrees with it. **Test independence gap (registered):** the predicate table itself is not derived from the frozen contract — the fixture carries no predicate — so a drift between the fixture adapter's assignment and the validator's assignment would be caught only by the oracle's per-operation reason/field-path comparison; the oracle does assert that comparison for all ten rejections.

The adapter comment chain (`adaptRg11Fixture` / `adaptRejection`) is the classifier contract until a stricter schema-side outcome declaration exists.

## Runtime Deviation Register

Registered deviations and their disposition. DEV-01/DEV-02 are fix-recorded runtime decisions mirrored by the oracle; DEV-03 is a ruling recorded for the record.

- **RG11-DEV-01 (fixed in runtime, oracle mirror aligned).** `correct_transaction_version` previously rejected every correction with `DOMAIN_REJECTED`: the shared `formalIdCollision(appended)` check judged the corrected record's own transaction id, previous versions, posting sets and postings as collisions, so the frozen `main-correct` accepted fixture could never pass. The check is replaced by `appendedIdCollision(appended, baseline)`, which subtracts the baseline's own legal references and checks only the ids the append newly introduces (the v2 version id) against the whole collection. The store test class contract documents the fixed behavior and the correction round-trip store test (RG11-QA-001/RG11-SPEC-002) covers the persistence path (see Unclosed Items). The oracle's `statistics-time correction appends version two with operation confirmation` asserts the accepted path.
- **RG11-DEV-02 (fixed in runtime, oracle mirror aligned).** Recognition report periods were rendered from a UTC text: the recognition record's `statisticsAtText` fell back to `kotlin.time.Instant.toString()`, which renders UTC and shifts report day periods by one day for evening instants of the case timezone. The runtime now renders the report text through the `localDateTimeText` helper at the fixed +08:00 offset (same civil-from-days arithmetic as the domain local calendar, byte-identical to the frozen `statistics_at`/`scheduled_at` texts).
- **RG11-DEV-03 (ruled, accepted).** Revision installment sequences continue globally across revisions (revision-02 continues 4, 5, 6 in revision order; the frozen validator demands "unique and consecutive in revision order"). The shard-1 domain helper restarts sequences at 1 per revision, so the application layer compensates by offsetting the built installments with the schedule's current maximum sequence (`sequenceOffset` in `revisePeriodicAllocation`). **已裁决：该补偿由应用层承担，domain helper 保持每 revision 从 1 开始，accepted as designed.**

## Persistence

`15.sqm` implements the additive v15 to v16 migration (D-085, aligned with the RG-08/RG-10 additive pattern): existing formal rows and all prior RG owners remain untouched. It adds one shared formal-chain column and creates 11 RG-11-exclusive tables and 30 triggers:

- **Shared column (1):** `transaction_version.confirmation_id` — the frozen corrected v2 version carries `confirmation_id`; the column is a shared formal-chain addition exactly like the v8 to v9 `canonical_kind` column (`9.sqm`), `NULL` for every pre-existing version, and write-once guarded (only a later version of a `PREPAID_RECOGNITION` transaction may carry it; `rg11_transaction_version_confirmation_guard_insert/update`).
- **Tables (11):** `rg11_operation` (outcome CHECK `PENDING`/`ACCEPTED`/`NO_CHANGE`/`REJECTED`), `rg11_returned_id`, `rg11_schedule` (typed edge onto its `PREPAID_PURCHASE` payment transaction), `rg11_revision`, `rg11_installment`, `rg11_revision_installment`, `rg11_confirmation` (subject `kind = 'operation'`, `subject_id = operation_id`, payload `'{}'`), `rg11_audit_link` (typed `periodic_allocation_recognition` edge), `rg11_posting_semantic` (role CHECK with per-role eligibility/category shape), `rg11_posting_reconciliation` (status CHECK `PENDING` only), `rg11_formal_transaction_metadata` (`created_at`, `statistics_at_text`).
- **Trigger families (30):** the two shared `transaction_version.confirmation_id` ownership guards; 24 immutable update/delete guards (one update + one delete per RG-11-exclusive table, plus the metadata statistics-time update allowance); `rg11_revision_number_sequence` (append-only, consecutive per schedule); `rg11_installment_sequence` (continuous per schedule across revisions); `rg11_schedule_formal_owner_guard_insert` (schedule payment transaction must be `PREPAID_PURCHASE`); `rg11_audit_link_target_guard_insert` (exact installment onto an exact `PREPAID_RECOGNITION` transaction); `rg11_posting_semantic_formal_owner_guard_insert` (`payment_asset` on `PREPAID_PURCHASE`, `prepaid_asset` on either kind, `expense` on `PREPAID_RECOGNITION`); `rg11_reconciliation_current_guard_insert` (PENDING only, eligible semantic only — RG-11 has no matching action).

Formal transactions continue through the shared chain (`ledger_transaction`, `transaction_version`, `posting_set`, `posting`). `Ledger.sq insertTransaction` maps the new kinds through the `canonical_kind` CASE: `PREPAID_PURCHASE`/`PREPAID_RECOGNITION` write `kind = 'EXPENSE'` (the legacy CHECK admits only the five old kinds) and `canonical_kind =` the new kind; reads use `COALESCE(canonical_kind, kind)` (D-085:1111, precedent `Ledger.sq` 1725-1740). `versionSixteenWiresPrepaidCanonicalKindsAndProtectsRg11Guards` asserts both canonical kinds survive write and reopen and that the confirmation-id and owner guards fire on bypass SQL. `SqlDelightRg11Store` claims the operation identity with its fingerprint, replays finalized identities, persists the runtime delta and finalizes the outcome inside one `transactionWithResult`; `persistAppendedVersions` writes the corrected v2 version row, its write-once confirmation id, the current-version advance and the `statistics_at_text` advance; failure injection at `AFTER_CLAIM`/`AFTER_DELTA` rolls back claim and delta atomically. Migration DDL atomicity is a caller contract: the v15 to v16 DDL is atomic only when the caller wraps `Schema.migrate` in a transaction (the failure test `versionFifteenToSixteenDdlFailureRollsBackEveryRg11Owner` exercises exactly that transactional path, RG-08 precedent). Schema version is asserted 16 in 13 sites across 8 files (Scope And Approval). `minSdk = 34` is declared in the ledger-data build (RG-09 v14 decision continuation).

## Known Records

- **`appendVersion` is the shared kernel; RG-12 `posting_facts` is reserved.** `TransactionVersionChange.Postings` and the `newPostingSetId` binding are implemented in the primitive but unused by RG-11; RG-12 will create a fresh posting set through the same primitive. `replaceNote` now delegates to `appendVersion` with `TransactionVersionChange.Note` and keeps the RG-01 call semantics unchanged (D-085 impact: RG-01 note_update regression covered by the existing suite).
- **`statisticsAtText` fallback renders UTC (hazard, currently unreachable).** `Rg11Runtime.statisticsAtText` falls back to `version.times.statisticsAt.toString()` when the record text is null; every RG-11 record currently sets the text explicitly (create uses `occurredAtText`, recognize uses `localDateTimeText`, correct uses the input `statistics_at` text, seeds carry the frozen `statistics_at` text), so the UTC fallback never fires today. The same UTC-rendering hazard sits in the data-class default texts (`Rg11CreateInput.startAtText`/`occurredAtText`, `Rg11CorrectInput.statisticsAtText`, `Rg11CorrectIds.confirmationCreatedAtText`) and in the store-side metadata fallback (`SqlDelightRg11Store.persistFormalRecord` writes `createdAtText ?: createdAt.toString()` and `statisticsAtText ?: ...statisticsAt.toString()` for seeds with null texts). A future path that forgets the text would shift report day periods; the fallbacks and defaults should be removed or made offset-aware when RG-12 lands (RG11-SPEC-004).
- **`splitAmountIntoInstallments` rejects a zero quotient (RG11-QA-002).** When `totalMinor < count` the integer quotient is zero and the split previously produced zero-amount installments; the domain now fails with `must_be_positive` (fail-closed hardening). The frozen contract only splits totals that keep every installment positive (`100.00` over 3, `66.67` over 2), so no frozen fixture exercises the boundary; the runtime surfaces it as `MUST_BE_POSITIVE` on `$.attempted_input.amount` through `domainRejected`.
- **Store seeds are formal-chain only (RG11-SPEC-003).** `SqlDelightRg11Store` accepts only `openingTransactions` — there are no schedules / revisions / installments / confirmations / audit links / posting-semantic seed parameters. `ensureOpeningTransactions` persists the formal chain and `rg11_formal_transaction_metadata` but never `rg11_posting_semantic` / `rg11_posting_reconciliation` rows, so a seeded formal transaction's reconciliation semantics (`rg11_posting_semantic` role/eligibility and the `rg11_posting_reconciliation` PENDING row) are not rebuilt after reopen; the derived reconciliation state recomputes from the semantic rows, so seeds lose their per-posting semantics across reopen (RG-08 store same-pattern precedent). Seeds are expected to carry their frozen time texts; when a seed's `createdAtText` is null, `persistFormalRecord` falls back to the UTC `createdAt.toString()` text (`SqlDelightRg11Store.kt` metadata insert).
- **Retry-by-identity does not re-validate the fingerprint (RG11-QA-004).** `RetryIdempotentInput` replays the finalized receipt by identity lookup only — in the store (`replayRetry`) and in the runtime (`Rg11Runtime.replayRetry`) — matching the RG-08 retry precedent; the same-identity replay with a full operation body re-checks the fingerprint and returns `RequestIdentityConflict` on change.
- **`ensureOpeningTransactions` guards only the first seed ledger (latent, RG11-QA-005).** The duplicate check queries `selectRg11FormalTransactions` for the first opening record's ledger only, so a seed list spanning multiple ledgers would re-persist the other ledgers' records on a second constructor pass and hit the formal-chain primary keys. Latent: RG-11 store usage passes single-ledger openings (`emptyList()` in every store test).
- **Crash paths fire only on corrupted state (RG11-QA-006).** `checkedAdd(...)!!` in `mergeReports`, and the `check(...)` / `error(...)` sites in the store (PENDING rows, unknown outcome codes, failed metadata/confirmation writes) and runtime (overflow, balance mismatch) are unreachable for contract-shaped inputs; they fail fast on corrupted persisted or derived state instead of producing wrong money.
- **`Rg11Runtime.replayRetry` is a dead path under the store (RG11-SPEC-005).** `SqlDelightRg11Store.commit` intercepts `RetryIdempotentInput` before the runtime and replays the persisted receipt itself (`replayRetry` in the store), so the runtime's retry branch is exercised only by the in-memory oracle; both paths behave identically (identity lookup, conflict on unknown identity).
- **The `localDateTimeText` helper assumes a whole-hour offset.** Offset minutes are derived from `utcOffsetSeconds % 3600` with a sign; the frozen contract only fixes `Asia/Shanghai` (+08:00, `DEFAULT_UTC_OFFSET_SECONDS = 28_800`), and the domain local calendar shares the same whole-hour assumption. Non-whole-hour offsets are out of contract.
- **The frozen `hidden` prepaid-account flag has no domain field.** The frozen catalog marks the prepaid account `hidden`; the domain `Account` carries no `hidden` field and no RG-11 action consumes it, so the flag has no runtime owner (projection rule 1 asserts only the representable catalog fields).
- `loadPersistedSnapshot` hard-errors on a formal transaction without `rg11_formal_transaction_metadata`; the store hard-errors on a persisted operation still `PENDING` and refuses to finalize `RequestIdentityConflict` (identity conflicts exist only inside the in-memory runtime session). Both are shared-formal-chain limitations with the RG-08/RG-09/RG-10 stores.
- Rejected and no-change receipts are persisted with their reason/field path (rejections) and returned ids (no-change), and replay the stored outcome; a retry by identity (`RetryIdempotentInput`) replays the finalized receipt without an operation body, and an unknown identity is a conflict.
- Recognition state is derived exclusively from `periodic_allocation_recognition` audit links; revisions are append-only with consecutive numbers; recognition results are never written back into domain payloads.
