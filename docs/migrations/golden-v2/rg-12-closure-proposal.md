# RG-12 Golden Schema v2 Closure Proposal

状态：active

## Authority And Boundary

This proposal records the D-085 closure candidate for RG-12 (reconciliation correction: `correct_transaction_version` with the `posting_facts` semantics). RG-12 is a direct-v2 scenario: the frozen contract `golden/rules/rg-12.json` (contract_version 2.0.0, approved at commit `efbb13a`) has no v1 mapping and no adapter by design, so there is no mapping gate; per D-085:1115 the closure gate status is recorded in this proposal's review disposition. D-085 approves the complete Kotlin runtime for the single closed action, the 12-operation fixture oracle (accepted 1 / no_change 1 / rejected 10; D-085:1107), and the formal SQLDelight persistence with the additive v16 to v17 schema migration (D-085:1113), built on the shared `appendVersion` domain kernel in its `Postings` form (fresh posting set through `newPostingSetId`, D-085:1109) and the shared `explicit_operation_confirmation` / `idempotent_replay` rules. No new `TransactionKind` is needed: the corrected v2 version of the frozen contract is an `EXPENSE` transaction (D-085:1111). Business semantics remain governed by the design document `docs/specs/2026-07-18-rg-12-reconciliation-correction-design.md` and the frozen Python semantics (`test_rg12_golden_v2.py`, 5 tests). This artifact records the implemented owners, the v2 compatibility projections, the classification and runtime-deviation decisions, and the proofs required before the closure gate is marked `approved`. It does not edit the frozen `golden/rules/rg-12.json`, `.external/`, or a publication target, and it renews no push authorization (D-085:1117: push was authorized once by the user and is executed only on user instruction). RG-12 is the final direct-v2 runtime; the remaining queue (RG-01/02 full comparison, publication gates for RG-03/05/10) is outside this proposal.

## Oracle Scale Disposal

The frozen fixture `golden/rules/rg-12.json` was independently counted for this proposal (the oracle's raw-operation-registry test asserts the same counts). It contains exactly 12 operation-shaped cases across three roots, and the oracle is implemented as a strict 1:1 mirror of those 12 cases (RG-08/RG-11 precedent: id-for-id, no completion logic, no synthetic expansion, no fixture rewrite).

| Root | Count | Entries |
| --- | --- | --- |
| `root-correction` | 2 | `root-correction-correct` (accepted), `root-correction-replay` (no_change, reason `idempotent_replay`, `retryOf = root-correction-correct`) |
| `root-rejections` | 10 | `root-rejections-reject-1` .. `root-rejections-reject-10` (all rejected) |
| `root-partial` | 0 | baseline-only root of the state graph: `state-partial-00` is a frozen initial state with no operations |
| **Total** | **12** | accepted 1 / no_change 1 / rejected 10 |

The accepted 1 / no_change 1 / rejected 10 split is read directly from the frozen `outcome.status` blocks (the direct-v2 contract carries explicit outcomes). The 10 rejections cover 10 unique frozen reason codes, one each (`complete_replacement_postings_required`, `replacement_postings_must_balance`, `duplicate_source_posting_id`, `known_account_required`, `owned_account_required`, `account_currency_mismatch`, `matched_unaffected_posting_must_be_preserved`, `explicit_confirmation_required`, `exact_decimal_string_required`, `historical_facts_immutable`); unlike RG-11 no reason fires twice. The single no_change op is `root-correction-replay`, whose `returned_ids` equal the first-time ids of `root-correction-correct`; retry equality is asserted (Classification Inference Registry). The rejection chain keeps baseline == result byte identical (D-085:1107).

The three roots' initial states are rehydrated verbatim from the frozen baselines and project onto them field by field. `state-partial-00` carries the pending liability fact (`root-partial-liability-v1` pending) and the partial summary; `state-correction-00` carries two matched facts and the matched summary; `state-rejections-00` additionally carries the **external CNY asset account** (`root-rejections-external`, real but not owned) and the **owned USD asset account** (`root-rejections-usd`) in its catalog — the accounts the rejection machinery exercises (known-account, owned-account and currency-mismatch rejections). The three initial states together hold the fixture's external and USD accounts; all other accounts are owned CNY real asset/liability or non-owned non-real expense pseudo-accounts.

## v2 Projection Registry

The oracle is an independent replay comparator, not a fixture-to-runtime identity copier. The registry is taken from the `Rg12FullStateOracleTest` class contract and the `Rg12FixtureReplay` adapter contract and is confined to the comparison layer, never altering runtime provenance, formal ownership, or append-only rows.

1. **Rejected ops share one frozen request id, synthesized per op.** All ten rejections carry the frozen `attempted_input.request_id` `root-rejections-request`. The runtime rejects a second commit with the same identity and a different fingerprint (`RequestIdentityConflict`), so the shared rejections are replayed under per-operation synthesized request ids (`<operation-id>-request`); the frozen `attempted_input.request_id` is not part of any frozen output state, so the projection is inert (RG-08 invalid-inputs / RG-11 `reject-request` precedent). The accepted `root-correction-correct` and its idempotent `root-correction-replay` keep the frozen shared request id `root-correction-request`, so the runtime returns the first-time ids on the replay.
2. **`rejectChangedMatchedAsset` dispatch.** The frozen rejections replay with `rejectChangedMatchedAsset = true` (the frozen rejection semantics: a changed matched asset leg is rejected with `matched_unaffected_posting_must_be_preserved`); the accepted `root-correction-correct` and its replay pass `false` (the frozen accepted-path semantics — the fixture asset leg stays unchanged, so no changed-matched-asset lineage is produced in the accepted path).
3. **Empty-string sentinel for unanchored invalidation entries.** `invalidation_entry_ids` is a non-null list in the typed boundary; the frozen nulls of the legs that are never invalidated are projected to the empty-string sentinel `""`. The runtime only consumes the entry of an invalidated real leg, whose anchor is always present (frozen `root-correction-match-liability-v1-history-2`). Every entity id of the contract is explicit in the frozen states and deltas and consumed through the per-request anchors of `tests/fixtures/rg12-runtime-input.json` (never reverse-read from expected result states); the `replacement_postings`-aligned id lists (`posting_ids`, `replacement_link_ids`, `invalidation_entry_ids`, `new_match_ids`, `new_match_entry_ids`, `new_match_invalidation_entry_ids`, `reconciliation_fact_ids`) are anchored as JSON arrays with explicit nulls. Rejected paths never consume ids, so the adapter synthesizes deterministic per-operation placeholder ids for them (`synthesizedCorrectIds`). Reconciliation record ids follow no uniform derivation rule, so the fixture exposes a postingId -> reconciliationId map assembled from the initial states' `posting_reconciliations` (input-side seeds) plus the per-request `reconciliation_fact_ids` anchors.
4. **`domain_entities` id-set normalization.** The collection order is a validator serialization artifact: the golden validator compares entities by id (`test_rg12_golden_v2.py` `by_id`), the runtime projects consumption records first and then matches (append order), so the state comparison normalizes `domain_entities` to a set of canonical JSON entries. The `status_history` array inside a match payload IS contractual (append-only sequences): the runtime renders it as one JSON text and the projection parses it back before comparison. The per-state catalog is static input no RG-12 action mutates; it is asserted separately on the representable fields (id/kind/currency/owned_by_user/real_account for accounts, id/parent_id/posting_account_id/active for categories) and excluded from the per-state collection comparison.
5. **Balances set normalization; delta balances sorted exactly.** The runtime emits catalog order while the frozen result states sort by account id; the validator compares balances as maps, so the order is not contractual and the state comparison normalizes balances to a set of entries. The delta `balances` value changes stay compared in the frozen sorted-by-key order (the Python generator demands that order).
6. **`sources` / `evidence` / `evidence_links` are immutable seeds.** No RG-12 action mutates them and the runtime does not maintain them, so the oracle projects them from the fixture seeds of the root (`Rg12StaticSeeds`); `candidates` and `relations` are always empty and projected as empty arrays. `audit_links` are the `posting_replacement` links: from/to `posting` endpoints and the closed `reconciliation_effect` payload.
7. **`derived_statuses` carry the `<rootId>-summary` id.** The runtime `reconciliationSummary()` map carries no status id; the frozen `derived_statuses` id follows the deterministic `<rootId>-summary` convention of the fixture (`root-partial-summary`, `root-correction-summary`, `root-rejections-summary`), so the projection derives it from the root id of the state being compared.
8. **Fixed +08:00 time rendering.** Times render in the case timezone `Asia/Shanghai` with a fixed-offset formatter (`SHANGHAI_INSTANT_FORMAT`, `ZoneOffset.ofHours(8)`); `kotlin.time.Instant` renders UTC, so the projection recovers the frozen strings byte for byte. The per-version `created_at` and `note` and the per-version `confirmation_id` are projected from the record-level `versionCreatedAtTexts` / `versionConfirmationIds` maps (the v2 version is created and confirmed at the frozen `corrected_at`). Entity change id lists and balance value changes are compared in the frozen sorted order; report/derived-status value changes and status changes entry order follows the Python generator's set iteration and is not contractual, so those three are compared as sets of canonical JSON entries (mirroring `test_rg12_golden_v2.py`). Status-change comparison writes absent sides as explicit nulls (frozen contract convention).

## Classification Inference Registry

The direct-v2 fixture carries explicit `outcome.status` blocks, so every operation is classified by its frozen outcome directly; the following inferences are registered for the parts the fixture leaves implicit:

1. **Retry (`root-correction-replay`) is `no_change` with the first-time ids.** The replay chain is derived from the input request ids (`firstRequestOwners` in `adaptRg12Fixture`): `root-correction-replay` carries the same request id as `root-correction-correct` and is classified `retryOf = root-correction-correct`. The runtime maps an identical-fingerprint replay to `NoChange` returning the first-time ids (D-085 retry equality, asserted in `idempotent replay returns no change with first-time ids`). The store replays a persisted `ACCEPTED`/`NO_CHANGE` receipt the same way (`replayOutcome`).
2. **Rejection predicates come from the primary domain chain — no per-op predicate assignment table.** Unlike RG-11, every frozen rejection is expressed as a typed `Rg12CorrectInput` and replayed through `validatePostingFactsCorrection`, which recomputes the exact frozen reason code and the exact indexed field path in the frozen first-failure order (unknown transaction / count / uncovered sources -> `complete_replacement_postings_required`, per-currency imbalance or non-numeric amount -> `replacement_postings_must_balance`, first duplicate source -> `duplicate_source_posting_id`, per-item known/owned/currency checks, changed matched asset -> `matched_unaffected_posting_must_be_preserved`, missing confirmation -> `explicit_confirmation_required`, first non-exact-decimal amount -> `exact_decimal_string_required`, any `history_mutation` -> `historical_facts_immutable`). The `Rg12InvalidPredicate` fallback table (`Rg12Runtime.rejectInvalidInput`) exists for attempted inputs that cannot be expressed as typed inputs; no frozen fixture uses it, and the oracle asserts the per-operation reason/field-path comparison for all ten rejections against the domain-carried paths. The authoritative source is the `CorrectTransactionVersionViolation` reasonCode/fieldPath table plus the `Rg12Operations` violation mapping; both must stay in agreement with the oracle mirror (`Rg12FieldPath` single-entry lookup).
3. **`changed_asset_case` symmetry on the accepted path (double-invalidation form).** With `rejectChangedMatchedAsset = false`, a changed matched real asset leg is expressed as symmetric lineage instead of rejection: the predecessor match appends exactly one `posting_replaced` invalidation entry at `corrected_at`, and a fresh inherited match for the same evidence is created (history-1 entry at the predecessor's last matched time) and immediately invalidated (history-2 entry at `corrected_at`, `new_match_invalidation_entry_ids`). The frozen contract has no accepted operation exercising this case (the fixture asset leg stays unchanged); the Python suite covers it (`test_changed_matched_asset_is_symmetric_and_requires_lineage_mapping`), and the Kotlin interface supports it end to end (see Unclosed Items).
4. **Reconciliation lineage is effect-derived.** `not_applicable` for non-real postings (no old fact, no fact created), `preserved` for unchanged eligible real facts (fresh same-evidence match with a history-1 entry at the predecessor's last matched time plus a `matched` fact), `invalidated` for changed eligible real facts (predecessor history appended at `corrected_at`, fresh `pending` fact); the derived summary moves `matched` -> `partial` for the corrected transaction. Balances and reports recompute from the current postings and are never seeded; reconciliation state never changes balances.
5. **Non-mutating outcomes keep the baseline byte identical.** Every rejected and no-change operation preserves the baseline state field by field and has zero formal effect; the oracle asserts projected baseline/result equality and frozen baseline/result payload equality for all eleven such operations (`rejected and replayed operations keep baseline and result byte identical`).

## Runtime Deviation Register

**No runtime deviations in this scenario.** All 12 frozen operations aligned with the runtime on the first replay: the oracle never required a fix, no `rejectChangedMatchedAsset`-path drift was found, and the ten rejections reproduce their frozen reason and indexed field path through the primary domain chain. The register therefore contains no DEV entries; the following non-deviation disposition is recorded for the schema:

- **RG12-SCHEMA-01 (registered, frozen-basis).** The v16 to v17 migration is additive except for one element: the two RG-11 shared `transaction_version.confirmation_id` ownership guard triggers are dropped and recreated byte-identically apart from the widened kind predicate — ownership now covers `PREPAID_RECOGNITION` **and** `EXPENSE` transactions. The frozen basis is the RG-12 corrected v2 version `root-correction-transaction-v2`: an `EXPENSE` transaction carrying `confirmation_id`. RG-11 behavior is unchanged: `versionSixteenToSeventeenPreservesFormalRowsAndCreatesEmptyRg12OwnersAcrossReopen` (`LedgerDatabaseMigrationTest`, lines 568-724) asserts the surviving v16 confirmation id, the EXPENSE insert succeeding under the extended guard (lines ~669-680), the write-once update still failing for the EXPENSE ownership (lines ~682-691) and `PREPAID_PURCHASE` staying outside the ownership (lines ~692-719); `versionSixteenWiresPrepaidCanonicalKindsAndProtectsRg11Guards` (lines 766-898) covers only the PREPAID canonical-kind wiring and the RG-11 guard protections (RG12-SPEC-001: the earlier draft attributed the EXPENSE guard extension assertions to the wrong test).

## Persistence

`16.sqm` implements the additive v16 to v17 migration (D-085, aligned with the RG-08/RG-10/RG-11 additive pattern): existing formal rows and all prior RG owners remain untouched. It creates 12 RG-12-exclusive tables and 29 RG-12 triggers, and rebuilds the 2 shared guard triggers described in the Runtime Deviation Register (31 trigger statements in total).

- **Shared column reuse (0 new):** the write-once `transaction_version.confirmation_id` column added by RG-11 (`15.sqm`) is reused as-is; the corrected v2 EXPENSE version carries it through the rebuilt guard.
- **Tables (12):** `rg12_operation` (outcome CHECK `PENDING`/`ACCEPTED`/`NO_CHANGE`/`REJECTED`, reason/field path columns), `rg12_returned_id` (FK cascade to the operation), `rg12_confirmation` (subject `kind = 'operation'`, `subject_id = operation_id`, payload `'{}'`), `rg12_formal_transaction_metadata` (`created_at`, `statistics_at_text`, statistics-time update allowance), `rg12_transaction_version_metadata` (per-version `created_at`), `rg12_posting_semantic` (role CHECK `expense`/`mixed_expense_asset_funding`/`mixed_expense_credit_funding` with per-role eligibility/category shape CHECK), `rg12_posting_reconciliation` (status CHECK `MATCHED`/`PENDING`, FK onto the semantic), `rg12_reconciliation_match`, `rg12_reconciliation_match_history` (append-only entries), `rg12_posting_replacement` (effect CHECK `PRESERVED`/`INVALIDATED`/`NOT_APPLICABLE`, `from_posting_id != to_posting_id`), `rg12_consumption_record` (amount kept as exact decimal text), `rg12_report_period` (day-period registry; values always recomputed, only the period list is stored).
- **Trigger families (29):** one update + one delete immutable guard per exclusive table (24), with `rg12_formal_metadata_guard_update` allowing only the statistics-time advance and `rg12_operation_guard_update` allowing only the PENDING -> final outcome transition with unchanged identity/action/class/fingerprint; `rg12_match_current_guard_insert` (a match owns an eligible real posting); `rg12_match_history_sequence` (consecutive sequences, entry 1 only on an empty history); `rg12_match_history_transition` (entry 1 `matched`/`exact_evidence`, every later entry `invalidated`/`posting_replaced` directly after a `matched` entry); `rg12_reconciliation_current_guard_insert` (write-once fact on an eligible real posting, fact status agrees with the match state: `matched` facts require an active match, `pending` facts forbid one); `rg12_posting_semantic_formal_owner_guard_insert` (semantics own postings of the current version of an `EXPENSE` transaction via `COALESCE(canonical_kind, kind)`).
- **Formal chain and queries:** the corrected v2 version goes through the shared `posting_set` / `posting` / `transaction_version` inserts with a fresh posting set; the per-version creation time and the write-once confirmation id are written through the RG-12 version metadata table and the shared `updateTransactionVersionConfirmationId`; the current version and the `statistics_at_text` advance are updated in the same transaction. `Ledger.sq` carries the rg12 claim/replay/select queries (144 rg12 references; RG12-SPEC-003 corrected the count from 90 lines to the actual 144 occurrences).
- **Store:** `SqlDelightRg12Store` claims the operation identity with its fingerprint, replays finalized identities (same-fingerprint replay of `ACCEPTED`/`NO_CHANGE` -> `NoChange` with the stored ids, `REJECTED` -> the stored reason/field path, changed fingerprint or unknown identity -> `RequestIdentityConflict`, persisted PENDING -> hard error), persists the runtime delta and finalizes the outcome and returned ids inside one `transactionWithResult`; failure injection at `AFTER_CLAIM`/`AFTER_DELTA` rolls back claim and delta atomically. The opening baseline is seeded once through the `Rg12Snapshot` constructor overload (`ensureOpeningState`, diffed against persisted rows so reopening is a no-op). Balances, reports, domain entities and the reconciliation summary are derived by the runtime and never stored.
- **Migration and version:** migration DDL atomicity is a caller contract: the v16 to v17 DDL is atomic only when the caller wraps `Schema.migrate` in a transaction (`versionSixteenToSeventeenDdlFailureRollsBackEveryRg12Owner` exercises exactly that transactional path, RG-08/RG-11 precedent); `freshVersionSeventeenAndMigratedVersionOneHaveEquivalentSchemaMetadata` asserts schema equivalence. Schema version is asserted 17 in 14 sites across 8 files (Scope And Approval). `minSdk = 34` is declared in the ledger-data build (RG-09 v14 decision continuation).

## Known Records

- **Store seed boundary: opening baselines must satisfy the SQL guards.** The `Rg12Snapshot` constructor overload seeds the full baseline (formal chain, semantics, matches with history, facts, links, confirmations, consumption records, report periods). Every seed row must pass the guards: `persistOpeningSemantics` requires a non-null role (`requireNotNull`), semantics must own current-version `EXPENSE` postings (`rg12_posting_semantic_formal_owner_guard_insert`), matches must own eligible real postings (`rg12_match_current_guard_insert`), facts must agree with the match state (`rg12_reconciliation_current_guard_insert`), and match histories must follow the sequence/transition rules. `ensureOpeningState` diffs against persisted rows, so constructing a store on an existing database is a no-op.
- **`ensureOpeningState` seeds a single ledger (RG12-QA-007).** The opening snapshot is seeded for the ledger of its first formal transaction only; RG-12 is a single-ledger contract and a multi-ledger opening snapshot is unsupported (a store whose opening snapshot carries no formal transaction seeds nothing).
- **Empty-string sentinel for unanchored invalidation entries.** Frozen nulls in `invalidation_entry_ids` are projected to `""` in the typed boundary; the runtime only consumes the entry id of an invalidated real leg, whose anchor is always present. Rejected paths never consume ids (deterministic per-operation placeholders).
- **`<rootId>-summary` naming convention.** The runtime `reconciliationSummary()` map carries no status id; the frozen derived-status id follows the fixture's `<rootId>-summary` convention and the projection derives it from the root id (projection rule 7).
- **Report periods are a seed registry; unseeded days never appear (RG12-QA-003).** `Rg12Snapshot.reportPeriods` carries the frozen report-registry day periods (including the zero-value correction day `2026-04-20`); `Rg12Runtime.reports()` emits one report row per seeded period plus every period of a record's `statisticsAtText`. A day that is neither seeded nor a record day would produce no report row — the correction-day zero report exists only because the fixture seeds it. The oracle and the store test assert the zero correction-day report.
- **`changed_asset_case` is pinned by a dedicated Kotlin store test (RG12-QA-002).** The frozen contract has no operation exercising a changed matched asset on the accepted path; `SqlDelightRg12StoreTest.changedMatchedAssetAppendsDoubleInvalidationLineageAndMovesSummaryToPending` pins the `rejectChangedMatchedAsset = false` double-invalidation lineage end to end through the store (fresh inherited match created at the predecessor's last matched time and immediately invalidated at `corrected_at`, `new_match_invalidation_entry_ids` anchor, `[MATCHED, INVALIDATED]` histories on both real legs, summary `matched` -> `pending`), mirroring `test_changed_matched_asset_is_symmetric_and_requires_lineage_mapping` of the Python suite.
- **`PostingFacts` amounts are compared as raw strings.** The domain exact-decimal check consumes the raw JSON text of the amount field (the frozen reject-9 amount is the numeric literal `110.0`, whose text `"110.0"` the exact-decimal check rejects), `sameAs` compares `amountText` byte for byte, and old-facts rendering goes through `minorToExactText` so frozen amount texts compare identically.
- **Crash paths fire only on corrupted state.** `checkedAdd`/`checkedNegate` in report merging, and the `check(...)`/`error(...)` sites in the store (PENDING rows, unknown outcome codes, failed metadata/confirmation writes, invariant violations on snapshot load) and runtime (balance mismatch, minor-unit overflow, id misalignment) are unreachable for contract-shaped inputs; they fail fast on corrupted persisted or derived state instead of producing wrong money.
- **`statisticsAtText` fallback renders UTC (hazard, currently unreachable).** `Rg12Runtime.reports()` and the store metadata insert fall back to `version.times.statisticsAt.toString()` (UTC) when the record text is null; every seed carries the frozen `statistics_at` text and a correction keeps the record's `statisticsAtText`, so the fallback never fires for contract inputs. It mirrors the RG-11 hazard registered as RG11-SPEC-004; the fallbacks and defaults should be removed or made offset-aware (Unclosed Items).
- **`correctedAtText` defaults to the UTC `correctedAt` rendering (hazard, currently unreachable; RG12-SPEC-002).** `Rg12CorrectInput.correctedAtText` defaults to `correctedAt.toString()` (UTC); the fixture adapter always passes the frozen corrected-at text and the runtime only consumes the text for the v2 version metadata and the confirmation timestamp, so the default never fires for contract inputs. Recommended hardening: make the field mandatory or offset-aware (Unclosed Items).
- **Retry-by-identity does not re-validate the fingerprint (RG-08/RG-11 pattern).** `RetryIdempotentInput` replays by identity lookup only — in the store (`replayRetry`) and in the runtime (`Rg12Runtime.replayRetry`); a same-identity full-body replay re-checks the fingerprint and returns `RequestIdentityConflict` on change.
- **Shared-formal-chain limitations.** `loadPersistedSnapshot` hard-errors on a formal transaction without `rg12_formal_transaction_metadata`; the store hard-errors on a persisted operation still `PENDING` and refuses to finalize identity conflicts (identity conflicts exist only inside the in-memory runtime session). Both match the RG-08/RG-09/RG-10/RG-11 stores.
- **Corrections preserve versions and never change balances.** The old version v1, its postings, evidence and match history stay immutable; the correction appends v2 and the replacement lineage; balances and reports recompute from the current postings, and reconciliation state is never a balance input.
- **Rejected and no-change receipts are persisted** with their reason/field path (rejections) and returned ids (no-change) and replay the stored outcome; the frozen `hidden` display flag and account `name` fields have no domain field (projection rule 4 asserts only the representable catalog fields).
- **`countRg12FormalTransactions` counts the shared formal chain (RG12-QA-009).** Despite the RG-12 prefix, the query counts `ledger_transaction` rows of the ledger — the shared chain every RG owner writes to — so on a shared ledger it includes transactions owned by other RG owners; the RG-12-exclusive row counts are the `rg12_*` tables. The migration and store tests use it only on ledgers whose formal rows are all RG-12-relevant.
